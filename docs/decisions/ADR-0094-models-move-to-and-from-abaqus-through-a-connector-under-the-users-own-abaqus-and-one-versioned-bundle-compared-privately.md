## Context

One of the team is building a tension coupon in Abaqus/CAE to the standard the studio offers (D3039). The founder asked which of the files we need to learn from it, and whether a script in our backend can read them.

- **The way out today** is the job's solver input (`.inp`), which Abaqus/CAE imports as a mesh without geometry, and the package document's step-by-step guide, followed by hand.
- **The way in today** is the command line on the founder's machine: `abaqus_reader` reads a deck, `equivalence` compares two models item by item, and the package's `5-verify/` scripts read an ODB and judge every output by zone (ADR-0089 amendment 3). The hosted site takes no model.
- **`.odb` and `.cae` are binary.** Every open-source reader of them found on 2026-11-12 runs inside Abaqus's own Python (see Why). The hosted tier has no Abaqus and cannot have one: the only licence is a teaching licence on the founder's machine (`fea/tools/run_abaqus.py`).
- **Runs are not private.** `records.list_jobs` and `GET /v1/coupon-jobs` list every job to every signed-in user; only projects check an owner (`records.owns_project`).
- **The workspace never names Abaqus** (ADR-0091, `BANNED_TERMS` in `lib/studio-copy.ts`).
- The team's models never enter this repository (ADR-0042), and only the unnotched tension coupon is offered (ADR-0089).

## Options considered

1. **Files by hand**: the user exports reports from CAE and uploads them with the deck. Rejected by the founder: "we need to be able to read his files without him downloading csv per csv".
2. **Read `.odb` and `.cae` on our server with an open-source library.** Rejected: none was found that works without Abaqus.
3. **Run Abaqus on our server.** Rejected: no licence that allows it (ADR-0056).
4. **The results file** (`.fil`, which a deck may ask for and which is documented and readable without Abaqus). Kept as a later, optional route. It does not carry the model as built in CAE, the user must edit the deck, and whether it carries every ply's values is UNVERIFIED.
5. **A connector that runs under the user's own Abaqus and writes one bundle; a build script for the way out.** Chosen.
6. **For the assistant, adopt an agent framework** such as FEA_Assisted_Agent (three tools in a loop on one fixed cantilever, no tests). Rejected: the pattern of three tools is kept, its code is not, and no model writes a number (ADR-0001).

## Decision

1. **One bundle, one format, both directions.** A zip with a manifest (`bundle_version`, the unit system as stated, the Abaqus version, the connector's version, the time, a SHA-256 per file), the `.inp` as solved, the model as built (parts, sections, layup, orientations, materials, boundary conditions, step and mesh controls, read from the `.cae` into JSON), the results per element and ply in the columns of `abaqus_every_output.py` with the reactions, and the `.jnl` as text. A bundle that breaks a rule is refused with every reason (ADR-0003). Nothing in a bundle is ever executed by us: a `.jnl`, `.rpy` or script is stored and read as text.
2. **The way in is a connector**: one script, the standard library only, run by the user with their own Abaqus. Version 1 is one command that writes the bundle from a job's `.odb` and its `.cae`. A menu in CAE ("Send to Anisotropy", "Open from Anisotropy") and a watched folder come after it.
3. **The way out is a build script.** Beside the `.inp`, the studio writes a script from the same spec that CAE runs (File > Run Script) to build a native, editable model: geometry, the composite layup, the step, the grips and the mesh.
4. **The comparison is ours, by tested code.** `fea/tools/abaqus_upload.py check|compare` joins the reader, `equivalence` and the every-output comparison, with ADR-0089's acceptance (the reaction and the gauge within 1 %, the free length within 3 %). A model on a different mesh is compared by position in the gauge and at the reaction, and the result says so.
5. **ADR-0089 amendment 3 stays.** The engineer's own run of `5-verify/` remains the audit's evidence. The upload adds the same comparison on our side, so that it shows beside the run.
6. **An upload is private.** It belongs to the user who sent it, is stored under its own prefix (`uploads/<id>/`) with an owner in a table of its own, and never enters this repository. The connector sends with a token the user creates. Confirmed by the founder: the founders also see an upload; nothing from an upload goes to the assistant's model provider in version 1; a stored bundle may train a later model only when it is the team's own, and an outside user's only by a box they tick.
7. **It shows as a card on the run's page, the answer first** ("Agrees with ours" or what differs, then the model, the pull force, the gauge section, between gauge and tabs), and as a chapter of its own in the document. The validation table keeps its three columns (the founder, 2026-11-08: "open source calculix is enough"). Confirmed by the founder, and a change to ADR-0091: this card, the menu and their downloads name Abaqus, because here it is the user's own program and not a tool of ours; the banned-term test allows the word in these components only.
8. **The assistant gets three fixed tools on the user's machine**: build from our script, run the job, send the bundle. It chooses among them; it writes no Abaqus script that is run and no number (ADR-0048, ADR-0052). Confirmed by the founder.
9. **Scope**: what `abaqus_reader` reads (flat S4 or S4R shells, one linear static step) for the tension coupon of ADR-0089. Anything else is refused with the reason.

Build order, one small pull request each: the bundle format and the comparison command; the connector; the build script; the assistant's tools; storage, tokens and the owner check; the card; the document's chapter; the menu and the watched folder; a bundle opened as a studio project; the results-file route.

## As built (2026-11-12, step 1: the bundle format and the comparison command)

- `fea/src/anisotropy_fea/bundle.py`: bundle version 1, `open_bundle` and `write_bundle`. The roles are `deck` and `every_output` (required), `reactions`, `model` and `journal`. The standard library only, Python 3.10 or later, so the connector can run it under Abaqus's own Python. A bundle may unpack to 256 MiB at most, a limit chosen without a measured job.
- `fea/tools/abaqus_upload.py`: `pack` (a bundle from a deck and the files `abaqus_every_output.py` wrote), `check` (what a bundle holds, and whether it is in scope) and `compare` (a bundle beside a run of ours, from that run's every-output file and deck). Exit 0 agrees, 1 differs or incomplete, 2 refused or out of scope; `--json` writes the result.
- `equivalence.equivalence_without_mesh` and `equivalence.outline`, for two models of one coupon on different meshes; `deck_equivalence` is unchanged.
- Differences from the plan: the results come as the every-output files, not as the field reports of `abaqus_report`, so that module is not joined. On another mesh the pairing is our element nearest each of their centroids, the gauge and the reaction are judged, and the free length is reported only. `compare` needs our deck beside our results. The model as built from the `.cae` has a role in the format and no reader yet: the connector writes it in step 2.

## As built (2026-11-12, step 2: the connector)

- `fea/tools/anisotropy_connector.py`: one command that writes `<job>-anisotropy.zip` beside a finished job's ODB. `abaqus python anisotropy_connector.py <job>.odb --units mm-MPa` reads the ODB with `abaqus_every_output.read` and takes the input file from beside it; no seat of Abaqus/CAE is used. `abaqus cae noGUI=anisotropy_connector.py -- <job>.odb --units mm-MPa --cae <model>.cae` also reads the model as built into `<job>-model.json` (format 1: the parts with their composite layups ply by ply, the materials, the sections, the assembly, the steps with what each boundary condition, load and output request is in them, the constraints) and takes the `.jnl` beside the `.cae` as text. The deck system is stated with `--units`. Nothing is sent: the command writes one file. Exit 0 written, 2 refused with the reason.
- `fea/tools/abaqus_upload.py connector --out <zip>` writes what is handed to a user of Abaqus: the connector, `bundle.py`, `abaqus_every_output.py`, `abaqus_extract_fields.py` and a note of the two commands. `check` now counts what the model file holds and prints what the connector could not read; the model file is listed and never judged.
- Changed after the first run under Abaqus 2025 (see Why): the user's `.cae` is never opened, a copy in a temporary folder is, because opening one changes the file; under Abaqus/CAE our arguments are found from the ODB on, because its launcher drops the `--`; every ending is said on the terminal by the connector itself, because Abaqus/CAE writes a script's error in `abaqus.rpy` only and ends with exit code 0; `caeModules` is loaded before the model is read; a displacement's value and a request's variables are read from the step's states; each ply gets its angle in degrees and a symmetric layup its ply count; a value Abaqus marks as not set is written as null.
- Differences from the plan: the connector is four files kept in one folder, not one script, so that the bundle format and the ODB reader stay the tested ones. Reading a `.cae` needs Abaqus/CAE's own kernel, so there are two ways to start it, and the first takes no CAE seat. Under Abaqus/CAE the exit code says nothing, so the printed line is the answer. A group of the model that cannot be read is named in the file under `not_read` and the bundle is still written. A layup's coordinate system is given as Abaqus's own number for it, not resolved. The package's `5-verify/` folder is unchanged.

## As built (2026-11-12, step 3: the build script)

- `fea/src/anisotropy_fea/write_cae_script.py`: `write_cae_script(model)` writes, from the same `FEModel` the deck is written from, a script that Abaqus/CAE runs to build the coupon as a native model: the outline as a sketch, the partition lines, the material with its strengths, the composite layup ply by ply on a coordinate system of its own, the grips (node sets held directly, or reference points with kinematic couplings), the step, the edge seeds and the structured mesh, the output requests at each ply's middle, and a job. Every number in it is a literal our code wrote, in the deck's unit system; the script computes only midpoints to pick faces and edges. `fea/tools/abaqus_build_script.py <coupon>.toml` writes it.
- Two ways to run it: File > Run Script in Abaqus/CAE, which adds the model and its job to the open session and saves nothing; or `abaqus cae noGUI=<script>.py -- save=<model>.cae`, which also saves the model and writes the job's input file. The script adds one model and one job, stops when either name is taken, never saves over a file, and says its own ending on the terminal.
- The coupon package carries it: `2-our-model/abaqus/<coupon>-build.py` beside the input file, listed in the package's README and in its verification steps (`docs/models/coupon.py`), for the unnotched tension coupon on a structured mesh. Any other coupon gets no script and its package is unchanged.
- Changed after the round trip under Abaqus 2025 (see Why). Abaqus/CAE writes a material's numbers into an input file with six significant digits, so in the upload's comparison two material constants that are one number written to six digits count as the same, and the item says so; `deck_equivalence` stays exact unless it is asked (`material_digits`). With kinematic couplings Abaqus puts the reaction on the reference points, which are nodes of the assembly and of no instance, so `abaqus_every_output.read` now reads those too.
- Differences from the plan: the six-digit rule is a choice made while building, not one the founder was asked about; it applies in `abaqus_upload.py compare` only and can be taken out by one argument. The probes' printed tables of the deck (`*Node Print`, `*El Print`) are left out of the script, because Abaqus/CAE has no object for them and what comes back is read from the ODB. Scope is the unnotched tension coupon: a hole, a dog-bone, an isotropic material, a force on nodal grips and rows that do not divide evenly are each refused with the reason.

## As built (2026-11-13, step 4: the assistant's three tools)

- `fea/tools/abaqus_tools.py`: `build`, `run` and `send`, for one coupon's spec in one work folder, on the machine that has Abaqus. `build` writes the build script into the folder and starts `abaqus cae noGUI=<coupon>-build.py -- save=<coupon>.cae`; `run` starts `abaqus job=<job> input=<job>.inp interactive`; `send` starts the connector under Abaqus/CAE on the finished job with its `.cae`, then compares the bundle with our own solve of the same spec (`abaqus_upload.compare`) and writes `<job>-comparison.json`. `plan --tools ...` runs several in the order given, and `state` says which are done.
- Nothing in a command is free text: the model's and the job's names are the ones our code derives from the spec, checked against letters, digits, `.`, `_` and `-`; every file argument is a bare name in the work folder; no shell is used. A tool whose output is in the folder is refused, so nothing is written over; a chain with a gap (send before run) is refused whole before anything runs; a tool judges by the files it finds and never by Abaqus/CAE's exit code. Every call is written to `<work>/abaqus-tools.json`: the tool, who chose it and from which words, the command as run, when, how long, what was said, and each file with its size and SHA-256.
- `api/src/anisotropy_api/abaqus_round_trip.py`: `python -m anisotropy_api.abaqus_round_trip "<what you want>" --coupon <spec> --folder <work>`. `Assistant.choose_tools` is new on the one interface of ADR-0052. With the assistant on, the model is given the sentence, each tool's name and description, and the names of the tools already done; it answers in a schema that holds names from those on offer and nothing else, and `tool_guard` keeps the names on offer, once each, in the tools' own order. With the assistant off, or when the model gives no answer, the sentence is not read and every step that is not done runs, and the command says so.
- What the model sees and writes: no file, path, coupon name or result goes to it (part 6), and nothing it writes reaches a command, because a name is looked up and never passed on. The verdict and every number are printed by the tools from tested code (ADR-0001).
- Changed after the run under Abaqus 2025 (see Why): `send` names the model to read in the `.cae`, because the file Abaqus/CAE saves for the build script also holds its own empty `Model-1` and the connector refuses to choose between two; the command's own lines are written at once, so they come before the tools' lines and not after.
- Differences from the plan: until an upload has somewhere to go (step 5), `send` does not send; it hands the bundle to the comparison on the same machine. The model chooses the whole chain once, before anything runs, and code runs it and stops at the first refusal; it is not asked again after each tool. The tools take a coupon's spec file, so they serve a checkout of this repository; a user of the hosted site has no command to start them yet (steps 5 and 8).

## As built (2026-11-13, step 5: uploads, private storage, tokens and the owner check)

- Migration `0010` and `api/src/anisotropy_api/records.py`: `abaqus_uploads`, one row per stored bundle (its owner, the bundle's SHA-256 and size, what the check found, the object key, the token it came with, and once compared the job of ours, the verdict and the comparison), and `upload_tokens` (the SHA-256 of a token, its last four characters, when it was last used and cancelled; never the token).
- `api/src/anisotropy_api/uploads.py` and nine routes in `main.py`. `POST /v1/abaqus-uploads` takes the bundle's zip as the request's body from a signed-in browser; `POST /v1/connector/uploads` takes the same from the connector with `Authorization: Bearer <token>`; `GET /v1/abaqus-uploads` lists, `GET .../{id}` opens, `GET .../{id}/bundle` gives the same bytes back, `POST .../{id}/compare` compares again, `DELETE .../{id}` removes the bundle and then the row. `POST`, `GET` and `DELETE /v1/upload-tokens` create a token (shown once), list them and cancel one.
- The bundle is judged by step 1's command, started as every tool of the fea package is: `abaqus_upload.py check`. A file that breaks the format is refused, 422, with every reason, and nothing is stored. A bundle out of the comparison's scope is stored and marked so.
- The owner is a project's ([ADR-0062](ADR-0062-the-chat-becomes-a-workspace-product-a-solver-independent-project-three-columns-one-panel-per-step-the-assistant-beside-it.md) part 6): the signed-in email behind Cloudflare Access, the actor locally. To anyone else every route answers "No upload ... of yours", 404. The founders are named by email in `ANISOTROPY_FOUNDER_EMAILS`; they list, open and download every upload and cannot compare or delete one.
- Storage: one object, `uploads/<upload id>/bundle.zip`, in the bucket when the settings name one (`ObjectStore.delete` is new), else under `.local/abaqus/` on the local disk (`storage.FolderStore`). The key is outside every coupon's prefix, so no container restores it.
- The comparison on the server is `abaqus_upload.py compare` beside a finished coupon job's own files, taken from that job's package (its `4-results/ours-every-output.csv` with the JSON, and its deck), from the disk or from the package's zip in the bucket. The job is the one `job_id` names; with none named, the owner's newest finished job of the coupon the bundle names. It runs inside the upload's request; when it cannot be made the upload stands and its row says why.
- The token: 256 random bits after `anisotropy_upload_`, at most ten live per person, cancelled by its owner. Behind Cloudflare Access the connector's route passes without Access's token only with `ANISOTROPY_CONNECTOR_UPLOADS=on`, POST alone, and its handler then checks the upload token before any of the body is read. Every other route still needs Access's token.
- `fea/tools/anisotropy_connector.py` 0.3.0: `--send <the API's address>` posts the bundle just written to that route. The token comes from `--token-file` or `ANISOTROPY_UPLOAD_TOKEN`, never from the command line (Abaqus/CAE writes its arguments into `abaqus.rpy`), and is never printed. The address is https, or this machine. A redirect is not followed. The command prints the upload's id and the verdict; when sending fails the bundle stays beside the ODB and the reason is said (the script ends with 1, which Abaqus's launcher on Windows does not pass on: see the eighth run).
- Differences from the plan, and what is not done:
  - The plan waited on our own sign-in (pull request #117), which was closed on 2026-11-13: the site keeps Cloudflare Access. So the connector reaches the hosted site only after two changes that are the founder's and are not made: a bypass policy for the path `/api/v1/connector/uploads` in the Access application, and `ANISOTROPY_CONNECTOR_UPLOADS=on` in the API's settings. Until then the hosted site takes an upload from a signed-in browser only, and no page sends one yet (step 6).
  - An upload writes no run record ([ADR-0026](ADR-0026-run-record-contents-and-startup-policy.md)): the run records are read by every signed-in user, and an upload is private. Its own row is its receipt, with the API's version and commit in the comparison.
  - Coupon jobs are not owner-scoped yet, so a `job_id` may name any finished job, as `GET /v1/coupon-jobs` already shows them to every signed-in user; the default picks among the owner's alone.
  - `may_train`, part 6's box, is a column that is false unless the upload sends it; no page has the box and nothing reads the column.
  - A token has no expiry. The size of a bundle as sent (50 MB), the uploads a person may store (100) and the live tokens (10) are the drafter's choices, not the founder's.
  - `abaqus_tools.py send` (step 4) still compares on the same machine and does not use `--send`.

## As built (2026-11-13, step 6: the card on the run's page)

- The card: `components/studio/abaqus-card.tsx`, with its calls and words in `lib/abaqus-exchange.ts`. `ResultsView` shows it under the summary of a finished unnotched tension run, in the workspace and in the viewer window, when the API says uploads are kept. The page computes nothing ([ADR-0001](ADR-0001-deterministic-engine.md)): every number is the comparison's.
- Without a file it is three steps. "Open in Abaqus/CAE": the build script as a download. "Run the job, then the connector": the connector as one zip and its command. "Send to Anisotropy": a drop zone and a file chooser for `<job>-anisotropy.zip`. One sentence says who can see the file and the largest size.
- With a file the answer is first: "Agrees with ours", "Differs in N places", "Not every part could be compared" or "Not compared". Then four rows: the model, the pull force, the gauge section, between gauge and tabs, each with one sentence and its mark; a row's "Show" frames the place of its largest difference in the viewer when that element is in the mesh shown. "What differs" lists each item with the user's value beside ours and the place. "Details" holds the model item by item, the zones quantity by quantity and the file's facts. Below: Compare again, The file you sent, Send another file, Remove, and the files sent earlier for the same run.
- A refusal is said in the page's words with the API's reasons under "Why": a file the connector did not write, one too large (never sent), the limit of stored files, a run whose files are gone, a model the comparison does not cover.
- "Send straight from Abaqus" appears only where the connector's route is open: an upload key is created with a name, shown once with "Save as anisotropy-key.txt" and Copy; the command to add names `--token-file` and never holds the key; the keys are listed with Cancel. While this part is open the card asks every 5 s for a file sent from Abaqus and shows it when it arrives.
- `fea/tools/abaqus_upload.py`: `compare` adds `summary` to its result (how many places differ; the model's items counted; for each zone the quantity with the largest difference, its place and both numbers; the unit labels), and its printed text is written from it. `tests/fixtures/abaqus/` holds four results of the public D3039 check as the command writes them (agrees, differs, another mesh, no reaction), pinned by a test and read by the page's tests.
- `fea/tools/run_coupon.py`: a run whose package holds the build script reports it as the output `abaqus_build`. The Files list does not offer it; the card does.
- The API (`main.py`, `uploads.py`, `records.py`): `GET /v1/abaqus-exchange` says what the card may offer (uploads kept, the connector's route open, the three limits); `GET /v1/abaqus-connector` hands out the connector's files as one zip, written by `abaqus_upload.py connector` once per process; `GET /v1/abaqus-uploads` takes `job_id` and `mine`; `GET /v1/abaqus-uploads/{id}/bundle` also takes the actor as `?actor=`, because the page offers it as a link and a link carries no header.
- The words ([ADR-0091](ADR-0091-the-workspace-speaks-to-the-customer-in-the-products-own-words-mapped-in-the-page-and-guarded-by-a-test.md), part 7 here): the card's root carries `data-names-abaqus`, and `lib/studio-copy.ts` names what it may say that the rest may not, "Abaqus" and ".py" (`ABAQUS_CARD_ALLOWS`). The banned-term test reads the card apart from the page: the card holds those two and no other banned term, the rest of the page none. "Bundle", "ODB" and "equivalence" are not on the card's first screen.
- The card's numbers follow the site's one rule (ADR-0091 amendment 1, merged from `main` the same day): four significant figures, no exponent in letters, the minus sign. Its own numbers go through `printed` and `formatNumber`, and a sentence of the comparison through `inProse` (`cardText`).
- Differences from the plan, and the drafter's choices the founder has not been asked about:
  - "Open in Abaqus/CAE" is a download and one sentence. A browser starts nothing on the user's machine.
  - "The bundle arriving" is progress while the page sends and the server compares. A file sent by the connector is found by asking again, and only while "Send straight from Abaqus" is open; nothing is pushed to the page.

## As built (2026-11-13, step 8: the menu in Abaqus/CAE and the watched folder)

## Consequences

- A user with Abaqus moves a model either way with one action and no export by hand; a user without Abaqus loses nothing.
- We depend on the Python inside the user's Abaqus. Abaqus 2025 runs Python 3.10 (`docs/installation-fea-tools.md`); which older versions the connector supports is open.
- The connector is our code on a user's machine, and the repository has no licence file. It cannot go to an outside user before the founder chooses one. Since step 6 the site hands it to every signed-in user, so the choice comes before the invite list grows beyond the team.
- Showing runs to their owner only is a separate change, needed before outside users.
- The teaching licence allows the team's comparison only, never a customer deliverable.
- A new table, a new storage prefix and a token are added to the hosted tier.
- Once the founder opens it, the connector's route is the one path of the API that Cloudflare Access does not guard: an upload token stands in for the sign-in there, and whoever holds a live token can store bundles in its owner's name until it is cancelled (R-22).

## How we will know it was wrong

- The model that the build script makes in CAE does not reproduce our deck's answer within ADR-0089's acceptance on the D3039 check.
- A user's Abaqus cannot run the connector (its version, or a rule of their company): the results-file route or files by hand becomes the first route.
- An open-source library reads `.odb` without Abaqus: reading on our server is considered again.
- The bundle format needs a second breaking change within three months of version 1.
