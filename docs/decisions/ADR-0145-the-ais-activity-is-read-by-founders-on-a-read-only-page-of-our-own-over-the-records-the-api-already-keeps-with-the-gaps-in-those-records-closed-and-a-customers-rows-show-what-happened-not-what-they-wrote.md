## Context

- On 2026-11-26 the founder asked to oversee the AI (his words above). The review written for him that day (the Claude Doc "Overseeing the AI: orchestration, MCP and APIs", 2026-11-26) read the code and listed what is recorded and what is missing.
- Before this change, every call the API makes to the model left from one function, `ClaudeAssistant._ask` in `api/src/anisotropy_api/assistant.py`, and was kept as a row of `model_calls` (ADR-0120). A plan was a row of `agent_plans` (ADR-0144). A request was a run record in `runs` (ADR-0026).
- Nothing showed them together. Reading them took SQL: the costs' views (ADR-0120) and `assistant_guards_by_feature` (ADR-0139).
- Four things were not kept, or not pointed out:
  1. `planner.plan_with` gives the model one more try when its plan fails the checks. The answers the checks turned back were dropped.
  2. The words sent to the model were not kept in any form. A run record keeps the request the API received. It does not keep the instructions, the request and the answer form the API then sent to the model.
  3. A call was tied to its plan only through its run record's answer (`model_calls.run_id`, then the plan's id inside `runs.response`).
  4. `_ask` lets the provider answer a declined request with another model (`fallbacks="default"`). `model_calls.model` records the model that answered, but nothing held that model to the checked list (`CHECKED_MODELS`, ADR-0121 amendment 8, ADR-0139). The list was read only for the model the site is set to: at start, in `/v1/workspace/assistant` and by the check after a deploy.
- The code was written on 2026-11-26 and parked that day, because the founder asked to keep planning first. His go came on 2026-11-27.

## Options considered

1. **An outside tracing product, such as LangSmith.** It keeps and shows each prompt and answer. Rejected: every prompt and answer, customers' words included, would go to another company's servers unless it is self-hosted, and it is a second place to secure.
2. **OpenTelemetry's GenAI spans, sent to a tracing backend.** Rejected as the record: the conventions for agent spans are still marked Development, and a backend is a new service to run. Kept as a later export, not the record: a plan maps to an agent run, a `model_calls` row to a model call, a typed step to a tool run.
3. **A hosted agent platform's session viewer.** Rejected: we run no hosted agent loop today. The product has one planner, in our API: one call to the model, one more at most, and then the server carries the steps (ADR-0144).
4. **Our own read-only page over the records we already keep, with the gaps in those records closed.** Chosen. No new service, no customer's words leave our database, and the records exist.

Inside option 4, what a founder sees of a customer's words:

- **(a) Hidden.** A customer's rows show what happened, not what they wrote. The proposed default, after ADR-0104. The founder has not yet confirmed it.
- **(b) Visible to a founder who gives a reason, the reason logged.** Not built. Open for him.

Inside option 4, how a page left open keeps its feed whole. The first build asked, every 10 seconds, for what was newer than the newest event it showed. The independent review of 2026-11-27 showed that this loses events (see Why), and these were weighed:

- **(i) Ask for what is newer than the newest shown, with an overlap of some seconds, and drop the doubles.** Rejected: it holds only if no row is written later than the overlap. A plan's calls are written when its request ends, after a second call that can take as long as the model takes, so there is no such bound we can prove.
- **(ii) Read forward from the newest shown, page after page, until a page is not full.** Rejected: it fixes more new events than one read holds, and it still never sees a row written late with an earlier time.
- **(iii) Follow the database's own order of writing instead of the events' times (a transaction snapshot as the cursor).** Rejected: it rests on PostgreSQL internals that the three tables do not expose as a column, and it is far more to get wrong than the page needs.
- **(iv) Read again everything the page shows, from its oldest event on, and show that in place of what was shown.** Chosen. It needs no assumption about when a row is written: what is in the records from the page's oldest event on is what the page shows after each refresh. It costs one read of up to 200 events per refresh while the page shows 200 or fewer.

What options 1 and 2 say about LangSmith and OpenTelemetry comes from the review. Their own pages were not read again while this record was written: UNVERIFIED here, no source linked yet.

## Decision

Option 4, with (a) as the default until the founder chooses.

- **Who may read.** The three routes answer a signed-in founder only: an email that Cloudflare Access verified and that is in `ANISOTROPY_FOUNDER_EMAILS`. The email is read as the token states it, and it is a founder's only when it is a listed email but for the case of its ASCII letters: one with a character outside ASCII, or with space around it, is not (`oversight.is_founder`). Lower-casing and trimming alone would let two others through: the Kelvin sign lower-cases to "k", and a no-break space is trimmed. Anyone else, a customer or a service token, is answered 404 as if there were no such page, and nothing is read or kept. The check is the first thing each route does, before the actor header or any parameter is read, so anyone else gets the same 404 whatever else is wrong with the request; a founder is told what is wrong (422). A request with no sign-in at all is answered 401 by the sign-in, as on every route. Nothing else is under the three routes: another method on one of them, one of them with a slash after it, and any other path under `/v1/oversight` are answered exactly as an address with no route is, for anyone (`main.oversight_nothing_else`); the router alone would answer 405 with `Allow: GET`, or a redirect to the route, which says the route is there. A browser's preflight is answered by the CORS layer, outside the sign-in, as for every route. On a machine with no sign-in in front of the API, its one user reads (`main._overseer`).
- **Read only.** `oversight.py` writes nothing and calls no model. The page has no control: nothing can be paused, changed or approved from it.
- **Each view is kept.** A read of the feed, of a plan or of the weeks is a run record (ADR-0026) under `/v1/oversight/activity`, `/v1/oversight/plans/{plan_id}` or `/v1/oversight/weekly`, with who looked and how much they were shown. The exception is the page's refresh: a read of the feed with `since` or `from` is not kept, and every refresh asks with one of the two, on an empty feed too.
- **The feed**, `GET /v1/oversight/activity`: each call to the model, each plan and each approval, newest first. Events are ordered by time, then kind, then row, and each carries that as its `key`, so no two events share a place. It gives 50 events unless `limit` says otherwise, and 200 at most. `before` reads what is before a place, `since` what is after it, and `from` reads from a place on, the place included. A place is an event's key, or a time with its offset; a time with no offset is refused (422), as every time filter of the API refuses one, and so is a place that is not plain printable ASCII (the time's reader would take a NUL between the date and the hour). The answer also says `older`: whether the same reading has events past the ones given, which the feed knows by reading one row more of each kind than it gives. Each event says who it was for, what for, the model that answered, whether that model was checked, how it ended, the seconds and the cost.
- **How a call ended.** `declined` or `cut short` by the model. Else, for a plan's call: `turned back` when the checks turned its answer back, and the plan's state when its answer is the one the plan came to. The planner asks again after each answer it turns back, so the first calls of a plan, as many as it has answers turned back, are those; this is told only when the plan has the number of calls its turned-back answers say it must (one more than them; for a refused plan, as many or one more, since its last call may have given no answer to check). With any other count the records do not say which call was which, and each reads `plan` and the plan's state, such as `plan done`. Else `set aside`, `partly dropped`, `kept` or `not used`, read from its run record's answer; every route but a plan's makes one call for a request.
- **The refresh.** While its tab is in view the page reads the feed again every 10 seconds, counted from the end of the read before, so two reads never overlap; a hidden tab reads nothing and reads at once when it is shown again. A refresh reads everything from the oldest event the page shows on (`from` that event's key, or `since` 1970 when the page shows the feed from its beginning), 200 events at a time with `before`, until a read says nothing is older, and shows that in place of what it showed. "Show older" is offered only while the feed says there are older events, so a feed that fits its page exactly offers none. An event is therefore shown whenever its row was written, however many are new and however many share one instant; an event whose outcome changed shows the new one. New events grow the page to 1,000 events and no further, or to as many as it already shows once "Show older" has taken it past that: the oldest are then let go, and "Show older" brings them back, 50 at a time.
- **One plan's story**, `GET /v1/oversight/plans/{plan_id}`: the sentence, each answer the checks turned back with the reasons, each call with its own outcome, the approval, the version it made, each step as the page reported it, and the job.
- **The weeks**, `GET /v1/oversight/weekly`: the last eight weeks, this one counted, from the Monday (UTC) seven weeks before this week's, so every table starts on the same day and shows whole weeks. The guards' view (ADR-0139) and the costs' view (ADR-0120) per feature, the plans of each week by kind and state, the ten commonest reasons plans were refused, and the calls answered by a model outside the checked list.
- **The gaps in the records, closed** (migration 0018; the new columns are empty on the rows made before):
  - `agent_plans.attempts`: each answer of the model the checks turned back, with the reasons. What PostgreSQL keeps in no text and no JSON is replaced first, in every answer of the model, before the checks read it (`planner.storable`): a NUL and half of a surrogate pair by U+FFFD, and a number that is none (NaN, an infinity) by its word. So whatever is kept of an answer (an answer turned back, a plan's steps, a question asked back, a refusal's reason) and what the model is sent back for its one more try can be kept and sent, and one such character in an answer does not fail the engineer's request. An answer without one is as it was. The engineer's own sentence is never changed: one that holds a NUL or half of a surrogate pair is refused when it is asked (422, `schemas.PlanRequest`), and so is a repair's description that holds one, which comes with the sentence and is kept with it (`schemas.RepairPlanRequest`).
  - `model_calls.sent_sha256`: a fingerprint of the words sent, the SHA-256 of the instructions, the request and the answer form. The words themselves are not kept. Two calls with one fingerprint were sent the same words. The plan's story gives its first 12 characters.
  - `model_calls.checked`: whether the model that answered was in `CHECKED_MODELS` when the call was made. True or false from this change on, empty on earlier rows. A later change to the list does not change a row.
  - `model_calls.plan_id`: the plan the call was made for. It is emptied if the plan is deleted.
- **A customer's words (the default, awaiting the founder's confirmation).** On a row of anyone who is not a founder, the person is named by a tag: "customer" and the first ten hexadecimal digits of the SHA-256 of the email. The tag is a pseudonym that keeps an email off the page; it is not anonymity (see Consequences). The sentence reads "a customer's words, not shown". A step shows its number, role, tool and state, without its line or note. Left out: each answer turned back, the question asked back, the version's reason and change lines (their count stays), and the job's stage and message. No free text of such a row leaves the API, and a reason is free text: it writes values, units, names of regions and materials, and words of the sentence. So a reason is given as one of a fixed set of lines (`oversight.REASON_KINDS`), found by matching it against the planner's own wordings (`planner.py`, `planner_kinds.py`, and why a writer gave no answer, `assistant.py`), after "step N: " when it is one step's: "step 2: 2000 is not a number the sentence writes; …" reads "step 2: a value that is not a number the sentence writes". Only a reason the server wrote is matched. The records tell whose a refused plan's reason is: `attempts` keeps the checks' reasons for the last answer turned back, and the plan's reason is theirs when it is exactly those reasons joined (`planner.reason_of`). Any other is the model's own sentence (ADR-0144 amendment 1), or the plan is older than `attempts` and nothing tells whose it is: it becomes one line, "a reason in the customer's or the model's own words, not shown", and is never matched, because a model can write a sentence that reads as one of the checks' lines. A step's number is given only when the answer the reason is about has that step, which is the number the checks themselves gave it; a reason that leads with any other number is hidden whole, since that number could be one of the sentence. A checks' reason that matches no line becomes the same one line, and so does a tool's own refusal of a change (`oversight.reason_shown`, `reason_kind`). The same reading gives the story's reason, the reasons of each answer turned back, and the reasons the weeks count. A founder's rows, a robot's (a service token, which has no email) and those of a machine with no sign-in are shown in full.
- **The page**, `/ai`: "Now" (the feed, with a plan's story beside it when a row is picked) and "Weekly". The story is read again when the feed shows a row of the picked plan changed or a new one of it, and when its row is picked again; the read before is given up first, so one is out at a time, and the story shown stays until the new one is in. No menu links to it, and it asks search engines not to index it. A plan's row is picked with a button in it, so the keyboard reaches it, Enter and Space pick it, the focus shows, and the rows of the plan shown say so to a screen reader (`aria-pressed`); a click anywhere on the row does the same. What goes wrong is said where it shows: a feed that could not be read above the feed, and the page tries again at its next refresh, the first read included; a plan that is no longer in the records in the story's panel, with the feed left as it is; the weeks in their tab, with "Try again". An error goes when the reading next succeeds. A request that got no answer and a page built without the API's address are each said in fixed words. Anyone the API answers 404 for the page itself sees "Page not found", and the page stops asking.
- **Not built**: tabs for connections and agents, alerts, and controls (pause the planner, pause model calls, a limit per person). The review lists them as later steps.

## As built (2026-11-27)

- **API.** `api/src/anisotropy_api/oversight.py` holds the three readings (`activity`, `plan_story`, `weekly`), who a row is for (`who`, `tag_of`), a reason as its fixed line (`reason_kind`, `reasons_shown` and `reason_shown`, over `REASON_KINDS`), how a call ended (`call_outcome`, `turned_back_calls`), a place in the feed (`Cursor`, `cursor`, `key_of`) and whose email is a founder's (`is_founder`). The feed reads only the columns it shows (`CALL_SHOWN`, `PLAN_SHOWN`), so no plan's steps or turned-back answers. The routes, `_overseer`, `_place`, `_seen` and `oversight_nothing_else` are in `main.py`; `access.AccessMiddleware` keeps the email as the token states it (`email_as_signed`) beside the trimmed one the other routes read. `model_costs.sent_fingerprint` makes the fingerprint and `ClaudeAssistant._ask` sets it on the call. `planner.plan_with` reads each answer of the model through `planner.storable` and keeps what was turned back in `Planned.tried`; `schemas.PlanRequest` and `schemas.RepairPlanRequest` refuse a sentence, or a repair's description, the records cannot keep. `records.py` holds the new columns and `record_model_calls` writes them. Migration `api/alembic/versions/0018_oversight.py` adds the four columns, the index `model_calls_plan`, and the two indexes the feed reads `agent_plans` through: `agent_plans_created` (`created_at`, `id`) and `agent_plans_approved` (`approved_at`, `id`, approved plans only).
- **Page.** `app/ai/page.tsx`, `app/ai/ai.css`, `components/oversight/ai-activity.tsx` and `lib/oversight.ts`, which holds the reads, the feed (`firstPage`, `refreshed`, `withOlder`, and `watchFeed`, which lets one read run at a time), what the feed shows of one plan (`planRows`, which the story's re-read waits on) and the poll (`poll`).
- **Tests and contract.** `api/tests/test_oversight.py`, new tests in `api/tests/test_planner.py` and `api/tests/test_model_costs.py`, `tests/oversight.test.ts`, `tests/browser/ai-activity.spec.ts` (the page in a browser with the API played from the examples; the site's browser job runs it), and the examples the two sides share in `tests/fixtures/oversight/` (`activity.json`, `plan-story.json`, `weekly.json`).
- **Differences from the review's plan, and limits found while this record was written.**
  - The review planned a plan's id on run records too. It is on `model_calls` only.
  - Only the calls that plan are tied to a plan. The call that words a plan's answer goes through an answer route, which carries no plan (for a coupon, `/v1/workspace/result-answers`), and is not in the plan's story.
  - The page does not print the fingerprint. The plan route answers it.
  - A reason with no fixed line is hidden whole. On a customer's refused plan a founder may read only "a reason in the customer's or the model's own words, not shown", and must ask the customer or read the database to know more. That is so for every customer's refused plan made before migration 0018, whose row has no kept answers to tell whose words its reason is. A new wording in the planner needs its line in `REASON_KINDS`; a test holds the planner's checks to the list, and a wording it misses is hidden, not shown.
  - A refresh reads again everything the page shows: one request while it shows 200 events or fewer, one more for each further 200 after "Show older". One request to the feed is three queries of at most `limit` rows and one more each, read through an index (see Why), and the lookups of those calls' runs and plans.
  - `checked` compares the model's id as the provider reports it with `CHECKED_MODELS` by exact match, as the start-up check and `/v1/workspace/assistant` do. The one checked model today, `claude-opus-5-5`, has no dated id in the provider's model table, so no dated id can read "not checked" for it. What id the provider reports on the hosted site is UNVERIFIED: no real model was called for this record.
  - Migration 0018's downgrade drops the four columns with what they hold.
  - The two indexes on `agent_plans` were added to migration 0018 after its first writing. A database that ran the earlier 0018 (a developer's machine; no hosted database has run it) gets them by running 0018 down and up, and its downgrade drops them only if they are there.
  - The other routes that ask whether a sign-in is a founder's (`main._imports`, and `uploads.Uploads.sees_all` for the Abaqus uploads) still lower-case and trim the email. They are not changed here.
  - A person's rows are kept under the email with the space around it taken off, as every route records it. So a row of a sign-in whose email only trims to a founder's is shown as that founder's row to a founder; that sign-in itself cannot read the page.
  - A saved project whose name or content holds a NUL still fails where it is saved (`PUT /v1/projects/{id}`, 503), as before this change: seen while the plan routes were fixed, and not a plan's route, so not changed here.
  - The story is read again when the feed's rows of its plan change. A step that changes while the plan's rows stay as they are (a running plan's steps) shows after the row is picked again.
  - Not deployed. Migration 0018 has not run on the hosted database.

## Consequences

- Easier: a founder reads what the AI did, for whom, with which model and at what cost, without SQL. A plan's first answer and why the checks turned it back can be read later. A call answered by a model that was never checked stands out. A change of instructions shows as a new fingerprint.
- Harder: three more routes and a page to keep to the contract in `tests/fixtures/oversight/`. Every view but the refresh writes a run record. `agent_plans` rows grow by the answers turned back.
- We now depend on `ANISOTROPY_FOUNDER_EMAILS` for who may read: a wrong entry opens the page to that sign-in. The list is read as plain lower-case emails, and the other routes that ask for a founder read a sign-in's email less strictly than this page does.
- An engineer whose sentence holds a NUL or half of a surrogate pair is told so (422) and no plan is made; before, the request failed. What the model writes is cleaned of those before the checks read it, so a plan's kept steps can differ from the model's bytes by U+FFFD in their place.
- A request under `/v1/oversight` that no route takes is answered by a route of ours, not by the router: a new route there must be declared before `oversight_nothing_else`.
- A fingerprint says that two calls were sent the same words, not what the words were. To read the words, they must be built again from the code and the request of that day.
- The tag is a pseudonym, not anonymity. It is the first ten hexadecimal digits of the SHA-256 of the email with nothing added (no secret was added for it), so anyone who knows an email can work out its tag, and a founder can read the email itself in the database, beside every row. It keeps an email off the page and out of a screenshot of it. It hides a customer from nobody who has the records.
- A refresh reads more than a page that asks only for what is new: every 10 seconds, everything the open page shows. A page left open on a hidden tab reads nothing.
- Undoing migration 0018 loses what the four columns held: the answers turned back, the fingerprints, the checked marks and the plans of the calls.
- A founder cannot open a customer's sentence from the page, even to help that customer, until option (b) is decided.

## How we will know it was wrong

- A founder cannot answer "which model answered this plan, and was it checked" from the page alone.
- A customer's words, email or setup appear on the page or in an answer of the three routes.
- A founder needs a customer's sentence to settle a problem more than once a month: the default (a) is too strict.
- The page's reads slow the API: a read of the feed takes more than a second on the hosted database, or requests of the workspace slow while the page is open.
- Someone who is not a founder is answered anything but 404.
- An event is in the records, newer than the oldest event an open page shows, and not on the page after its next refresh.
- A reason on a customer's row holds a word, a value or a name from their sentence or their setup.
- We come to run more than one agent, or a hosted agent loop: revisit options 2 and 3.
