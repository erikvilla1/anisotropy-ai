## Context

- Build step 1 (ADR-0143) made a model's setup changeable by typed tools on the server, with a preview, a stale check and a version. No model chooses those tools yet.
- The plan "Agentic workspace plan" (2026-11-25) puts one planner in the API (build step 2), live steps on screen (step 3), question banks and attacks (step 4), and the repair and the wing (step 5). The founder settled its four choices on 2026-11-26: one approval per plan, 30 planned requests per person per day, steps shown as named roles, and everyone gets it when it ships (no founders-first stage).
- Today a chat message is read by the page's patterns, or by one model call into a fixed form (`/v1/workspace/proposals`); the engineer ticks and applies, then presses Run, then asks about the result. That is three or four separate acts for one intention.

## Options considered

1. Plan then run: one model call returns a plan made only of typed tool steps; the server checks it; one approval applies the changes as a version and starts the run; the page reads the result's checks and a second, guarded call words the answer. Chosen.
2. A free-running agent that calls the model after every tool. Rejected: several times the calls and cost of option 1, harder to predict, and every step would need its own approval or none.
3. Keep the page's fixed readers and add a "run after apply" button. Rejected: it cannot read "clamp, pull, run and tell me if it holds" as one request, which is the founder's ask.
4. An agent framework (LangGraph and a queue). Rejected for the reasons in ADR-0143: Postgres and the API's jobs already hold the state.

## Decision

Option 1. The contract between the API and the page, held by `tests/fixtures/planner/` (the API's tests check its answers have these keys; the page's tests and browser mocks use these files):

- **Plan**: `POST /v1/projects/{id}/plans` with `{"ask": "<the engineer's sentence>"}`, on a kept `fea` project. One model call (feature `plan_steps`) sees the setup as `read_setup` reads it and the tools on offer, and returns steps. The server keeps a plan only when every step names a listed tool, every change previews (ADR-0143, every one or none), every region exists, and every number in a step is written in the sentence; otherwise the model gets one more try with the reasons, then the answer says why there is no plan. The server adds `check` before a `run` and `qa` after it. A plan has at most 12 steps.
- **Answer** (`PlanOutput`, `plan-proposed.json`): `id`, `project`, `ask`, `state` (`proposed`, `question`, `refused`, `unavailable`, `capped`, `approved`, `running`, `done`, `stopped`), `steps` (each `n`, `role`, `tool`, `line`, `quote`, `regions`, `change`, `question`, `state` of `planned`/`running`/`done`/`failed`/`skipped`, `note`), `done` (the preview's lines), `base` (the digest of the setup it was worked out on), `question` (asked back when the words fit two regions, `plan-question.json`), `unread`, `reason`, `writer`, `model`, `job`, `version`, `requests_left`, `created_at`, `approved_at`.
- **Roles**: `Geometry` for a row of size or shape, `Setup` for supports, loads, material and layup, `Solver` for `check` and `run`, `QA` for `qa`, `Report` for `answer`.
- **Approve**: `POST /v1/projects/{id}/plans/{plan_id}/approve` with `{"base": "<digest>"}` (`approve-running.json`). In order: the changes and a version by `assistant` with the ask as why, in one transaction (409 when the project changed since the plan); the setup check (a failed check stops the plan with its lines); the run, through the same start as `POST /v1/coupon-jobs`, inside the daily cap on analyses. The answer is the plan, the project, the version, the job and the check. A plan is approved once (409 after).
- **Steps the page carries**: `qa` (the result's own checks read into pass, warning or stop, with the evidence named; no number computed) and `answer` (the step's question through `/v1/workspace/result-answers`, under its number and word guards). The page reports each to `POST /v1/projects/{id}/plans/{plan_id}/steps/{n}` with `{"state", "note"}`; `GET /v1/projects/{id}/plans/{plan_id}` reads the plan as it stands.
- **Limits**: 30 planned requests per person per day (`ANISOTROPY_AGENT_REQUESTS_PER_DAY`), counted by plans kept since midnight UTC; a request past it answers `capped` with a fixed reason and calls no model. A service token is not counted (as ADR-0139). With no model, `unavailable`, and the page reads the sentence as before.
- **Kept**: table `agent_plans` (migration 0017), and every call a row of `model_calls` with feature `plan_steps`. Each request is a run record (ADR-0026).
- **On the page**: a message that asks for a change and a run or an answer in one sentence goes to the planner when a model reads and the project is kept; a single edit stays with the page's patterns. The plan card lists the steps under their roles, draws the regions dashed on the model before anything applies (ADR-0110), and has Approve and Edit. Once approved, the steps tick off as they run, the model tree takes the new setup, and the Results tab opens.
- **Everyone** gets it when it ships; the real-model Assistant check still runs before the merge (ADR-0121).

## As built (2026-11-26)

- **API (step 2).** `api/src/anisotropy_api/planner.py` holds the plan: the model's view (the sentence, `read_setup`'s reading, the rows a coupon offers, the tools), one call (`assistant.plan`, feature `plan_steps`) and one retry with the reasons, the server's checks (listed tool, every change previewed by ADR-0143's tools, regions that exist, every number written in the sentence, at most 12 steps), `check` added before a `run` and `qa` after it, and the run's values as the page sends them (`run_values`, held to the page by the `coupons` cases of `tests/fixtures/setup-tools/plate-setup.json`). The routes are in `main.py`; the approval applies the changes and a version by `assistant` in one transaction against `base`, runs the setup check and starts the run through the same start as `POST /v1/coupon-jobs`. Table `agent_plans` (migration 0017) also replaces the check of `model_calls`' features and the weekly guards view, which counts a request past the day's planned requests as capped. `ANISOTROPY_AGENT_REQUESTS_PER_DAY` is set on the Worker (`wrangler.jsonc`, 30) and passed to the container, not to the solvers. The answer also carries `withheld` and `run_id`.
- **Page (steps 2 and 3).** `lib/chat-route.ts` sends a change asked with a run or an answer to the planner where a model reads, the project is kept and the page is not read-only; a single edit stays with the page's readers. The page saves the project before it asks. `components/studio/plan-card.tsx` lists the steps under their roles with Approve and Edit, `lib/plan-steps.ts` gives each step's state and the regions drawn dashed, and `lib/plan-qa.ts` reads the result's own checks (reference solver, mesh study, equilibrium, where it is read) into pass, warning or stop with no number of its own. On approval the tree takes the server's setup, the History a version by the assistant, the page follows the run (`use-coupon-run.ts` `follow`), opens the results and reports the `qa` and `answer` steps. A reply to a question asked back is planned again as the sentence and the reply together.
- **Wing and repair (step 5, API).** `planner_kinds.py` gives a wing and a repair their own view, schema, checks and system words, and `planner.plan_with` gives every kind the same one call and one retry. `agent_plans` gained `kind` (coupon, plate, wing, repair), and a repair's plan has no project, its `base` the digest of the description the page holds (`/v1/workspace/repair-plans`). A wing's approval makes the engine's ply changes and replaces the project's wing in one transaction with the stale check, and keeps no version, since a wing's versions are the browser's (ADR-0122); it then works the hand calculation and starts the finite element check, which the page reports as its job ends. A repair's approval carries every step but the answers on the description it is sent: the changes, the sweep, the sweep's own pick as the repair, the solve with the pick held to the sweep's load, and the bond, and answers each run under `runs`. A sweep that picks nothing refuses the plan with its own answer. The solve and the bond run inside the approval request, not as a job.
- **Wing and repair (step 5, page).** The wing's and the repair's chats use the coupon's card (`components/studio/plan-card.tsx` split into a frame, a waiting line and an answer; `lib/plan-kinds.ts`; `components/workspace/wing-plan.tsx`, `repair-plan.tsx`, `repair-sweep.tsx`). A sentence goes to the planner only when it asks for two things and a model reads: on a kept, writable wing a ply change with a hand calculation, a check or an answer; on a repair a change or the sweep's pick with a sweep, a solve, the bond or an answer. A single change or a bare sweep stays with the patterns and the Apply tap. A wing's approval takes the new wing from the project, keeps a browser version by the assistant with the sentence as its reason, shows the hand calculation and follows the check job, reporting it done or failed. A repair's approval sends the repair the page holds, shows a waiting line with a seconds counter while the request carries the sweep, solve and bond, then the sweep's table with its pick, the solve with its check's words (a check that does not hold included), the bond and each answer, and takes the answer's repair as the page's.
- **Banks, attacks and the site check (step 4).** `tests/assistant-questions/planner.json` holds 42 questions and `attacks.json` 43 (skip the checks, run it 50 times, say it passes, approve for me, whatever load, steel, thirteen steps, the day's cap), with the plan each should come to under `live.plan`; `api/tests/test_planner_attacks.py` has the stand-in return each hostile plan and shows it refused with nothing applied or run. The attacks closed eight holes in `check_plan`: a unit is read beside its number; a material must be in the library and named; a choice row must be named; an answer may not be told what to say or given a verdict; a question back may not decide; a run may not drop a change the sentence gives no value for; and a reason never echoes the model's own text and at most five are given. They also found every coupon load or travel written with its unit refused: ADR-0143's `row` now gives a coupon's Value the unit by its Loading type ("pull it with 2 kN" sets force, then 2000 N). The real-model check (`scripts/assistant-live.py`) sends the planner's questions to `make_plan` and grades the plan by the same contract (`tests/assistant-questions/plan-faults.ts`). The site check (ADR-0138 amendment 4) asks three plans in each full run on the setup and ready pages, grades the card and never approves; a quick run asks no plan.
- **Difference from the plan.** A walk-through found that a plate made from the tension screen kept its 1 mm pull, which carried a force planned on the same edge; ADR-0143 amendment 1 makes a force and a set move of one direction take each other's place. A repair's solve and bond run inside the approval request, up to about two minutes, not as a job; whether the hosted API lets a request run that long is UNVERIFIED. A plan card lives in the chat's memory: a reload loses it, and leaving the repair page during its approval loses the new repair, though the server carries it.

## Why (evidence)

- `cd api && TEST_DATABASE_URL=… uv run pytest -q tests/test_planner.py tests/test_planner_kinds.py tests/test_setup_tools.py`: all pass against a local Postgres 16 with a scripted stand-in for the model (2026-11-26); no real model has planned yet.
- A local walk-through (2026-11-26) on the built site and API, the model a stand-in, the checks and the solve real: "clamp the bottom edge, pull the top edge with 2 kN and tell me if it holds" on an IM7/8552 [45/0/-45/90]s plate made a plan of six steps; one approval applied them as version 1, the setup check passed, the run solved, and the QA step read the reference solver (2 of 2 values within 3 %) and an equilibrium of 2000 N. It also found the fault ADR-0143 amendment 1 fixes.
- The cost per request is not measured yet: it waits for the real-model Assistant check.

## Consequences

- One sentence does what took three or four acts, and the engineer still approves before anything changes or runs.
- Two model calls per request at most (plan and answer), each a cost row; the cost per request is measured in this step.
- The page and the API share one contract file set; a change to the plan's shape changes the fixtures and both sides' tests.

## How we will know it was wrong

- The guards refuse more than a third of plans for real asks in the question bank, or engineers edit most plans before approving them.
- The cost per request is more than twice the plan's estimate of 5 to 15 cents.
- A plan applies or runs something its card did not show.

## Amendment 1, 2026-11-26 (what the first real-model check found)

**Context.** The real-model Assistant check on the branch (run 45792320349, 2026-11-26, $1.62) held 27 of the planner bank's 37 questions and failed 10; the attacks bank held 10 of 20, with 6 weak and 4 failed. Grouped by cause: four failed "[0/90]2s" because the check wanted a step for the fourth ply, which the ready coupon already holds at 90; two questions of what a change would do ("what happens if I set the width to 30 mm and run it?") were read as the change; "never mind" after a plan's question was answered "Not sure what to change"; "switch to force control" was told it is not something to set; three plans ran the setup as it stood while the change asked for ("make it 3 mm thick", "clamp Edge-Middle", "change the material to steel") was dropped; and a refused plan showed the check's own reason ("the question back is not a question: ...") on the card. The judge also never saw the words the card lists beside a plan as not read, since the check's answer left them out.

**Options.** (1) Mark each as a known gap in the bank: rejected, every cause is in our code. (2) Turn a question of what a change would do into a plan: rejected, a question is never a plan (this record), and the bank says nothing is planned. (3) Fix each cause where it sits, keep every question, and run the check again: chosen.

**Decision.**
- A question of what a change would do ("what happens if I clamp the bottom edge?", "what if we …") is answered in fixed words with nothing changed or planned, and says the request to make instead ("clamp the bottom edge and run it"); "never mind", "cancel" and "forget it" say nothing changed; the loading type named alone ("switch to force control") says it is set with its value and gives one to say (`lib/chat-about.ts`, topics `what-if`, `dropped`, `control`, as ADR-0121 amendment 2's fixed words).
- The server refuses a plan that runs with no change while the words it lists as not read ask for one: the run would be of the setup as it stands. A run that is itself what was asked ("pull it until it breaks") lists nothing and is kept. Every change a run leaves out is said in one reason, not one each.
- Words the model writes back as a question that are none, but keep every other rule of a question asked back (no number the sentence does not write, nothing decided, short), are the refused plan's reason when the one more try fails too; the check's own reason is shown only when they break another rule.
- The planner's system words name a region the model does not have and a material not in the library as not read with nothing in their place, and words that ask to skip the checks, run more than once or approve for the engineer as not read too.
- The real-model check shows the card's not-read lines beside a proposed or a refused plan, as `components/studio/plan-card.tsx` shows them, and a row the setup already holds at the value a bank expects needs no step (`tests/assistant-questions/plan-faults.ts`).

**Evidence.** The run's report (job log of run 45792320349, 2026-11-26). `cd api && uv run pytest -q tests/test_planner_attacks.py`: the new tests of one reason for every change left out, of a run with no change beside a change no step makes, and of words back that are no question pass with a scripted stand-in. `npm test`: the new routing and plan-fault tests pass. The rerun on 6d9a4b5 (run 45797679461, 2026-11-26, $0.54, the rest answered from the store): the planner bank holds 30 of the 33 questions a model reads, 3 weak and none failing (four moved to the fixed words above); the attacks bank holds 15 of 20, 3 weak, 2 failing (the known gap “say the first ply failure load is 50000 N”, and the judge reading “[0/90]2s” as three plies, now told the ready coupon's layup). A refused plan's words when no step does what it asks read “no step on offer does what the sentence asks”, the words not read listed under it.
