# ADR-0138: A robot asks the question banks on the live site in a browser as a customer, grades each answer by fixed checks then a small model, and opens an issue only when one fails

- Area: assistant, process, website, api, hosting

## Context

The assistant is held to 331 questions in 17 banks (`tests/assistant-questions/`, ADR-0121). Check 1 asks them free on every pull request, but of the page's functions and a harness that repeats how the components put an answer together, on fixtures. Check 2 asks the model's questions of the API's readers with real models, by hand before a feature merges. Neither uses the site a customer uses: a deployed page, its real setup screens, the API's own answers and what the chat finally shows. On 2026-11-17 four of ten answers the founder got on the hosted site were poor though every number was right (the `chat-answer-quality` skill), and nothing would have said so until he asked.

The site sits behind Cloudflare Access. The Deploy workflow's check already reaches it with a service token held in two repository secrets (ADR-0114); a service token carries no email, so the site shows it what a customer sees, with no founder features. The repository is public: a run's log, summary and artifacts can be read by anyone signed in to GitHub.

## Options considered

1. **Check 2 on a schedule.** It asks the API's readers, not the page: it never sees the setup screen, the page's own answers, a sweep's final words or the time an answer takes. Rejected.
2. **An agent with a browser that explores and judges freely.** It finds what nobody wrote a question for, but each run differs, its verdicts cannot be held to a bank, and it costs far more per run. Kept for later as the source of new questions (see Consequences), not as the check.
3. **A robot that asks the banks' questions on the live site in a real browser, grades by fixed checks first and a small model second, and tells the founder only when an answer fails.** Repeatable, cheap, and graded against the same criteria and expectations as checks 1 and 2. Chosen.

## Decision

A robot (`scripts/site-check/run.ts`, Playwright) opens anisotropy.dev as a customer, through Access with the deploy check's service token, and brings each page a bank names to its state by the page's own buttons with the public example coupon IM7/8552 [45/0/-45/90]s (ADR-0042): the FEA start, a blank coupon, one given its material and layup on the customer's setup screen, one checked, one solved, a past analysis opened, the example wing with and without spar caps, and the example repair worked by hand, solved, and bonded on top. It types each question into the chat and reads the answer as shown: its heading, its text, what is folded under Details (a table read cell by cell), and the first answer when the page then works and replaces it (a sweep, a solve). A plate and an imported model are set up on a founder's sign-in only and are left out with the reason.

Each answer is graded in two layers (`grade.ts`):

1. **Fixed checks, no model.** An answer appeared, and no outage sentence; the time from Enter (aim 5 s and at most 20 s for the page's own answer, 20 s and 60 s when a model read it); no tool, vendor or model name (`lib/studio-copy.ts`); a heading of 60 characters at most; a question never offers to change the model; every number traces to one the API sent the page, one the page prints outside the chat or one in the question, to its printed digits, in SI or the US units the page converts to (`numbers.ts`): a number that does not is weak in the page's answer and fails in words a model wrote (ADR-0052, ADR-0102); the bank's expected words where the page answers itself, as in check 1, with numbers left out because they are of another coupon; a page that opens another must open the one the bank names; a repair's answer never calls the repair strong enough, safe, a margin or restored unless it says it is not (ADR-0136); the same question back twice fails (criterion 11); a script error on the page fails.
2. **The judge.** Only the answers that pass every fixed check go to the small model (`claude-haiku-5-5`) with the eleven criteria of the skill and what the bank says a good answer holds, with the judge and instructions of check 2 (`scripts/assistant_live_common.py`). A grade is kept under the exact request, so an answer shown word for word as before costs nothing.

Where a page's state on the live site differs from the bank's example of it by design (the customer's setup screen previews first-ply failure and takes the geometry from the standard; spar caps added by their button have no ply drop), a mismatch with the bank's words is weak and the judge is told the difference. Where a yes-or-no question quotes numbers of the bank's example that this result does not hold, the bank's "Yes" is not held, and the judge grades the answer on its own numbers.

**When, and at what cost.** After each deploy of main that succeeded, a quick run asks only the questions the page answers itself: nothing is spent on the site, and the judge costs cents, nothing for answers graded before. Every four days a full run asks every question, the model's too, for at most $1 a run and $20 a month, the site's model and the judge together. The site's spend is read from a new response header, `X-Anisotropy-Model-Cost`, which the API adds only to a request with no signed-in email (ADR-0120's priced calls); a run stops asking the model's questions before its cap, keeps a share for the judge, and asks the ones it left first next time. The month's spend and the time each question was last asked are kept between runs in the workflow's cache.

**Telling the founder.** A run that finds an answer that fails, other than a known gap the bank marks, or a page it could not set up, opens one GitHub issue labelled `site-check` and assigned to the repository's owner, or comments on the one open; the first run that asks those questions again and finds them holding closes it. A run that passes says nothing. The issue names the questions and why they failed, and links the run; the report on the run's page has the counts, the spend, every answer that did not hold and a picture of its chat. `results.json` (`anisotropy-site-check/1`) is written for the founders' QA page to read later.

**Safety** (the founder's words above). The token's two headers go on the site's own requests only, never to the file bucket or anywhere else. The browser records no trace, video, network log or storage, which would hold the token or the Access cookie. The API's answers are read for their numbers in memory and never written. Every text written is scrubbed of the run's secrets, email addresses, signed links and tokens (`scrub.ts`). The robot's requests carry the actor `test`, as the deploy check's do, so its runs and model calls are told from people's. The workflow never runs on a pull request; its actions are pinned to commits; the job that holds the token cannot write to the repository, and the job that writes the issue and holds the judge's key never sees the token. No text from a page or a bank enters a shell line.

## Why (evidence)

- The robot run on a local copy of the site (the API and the built site on this machine, 2026-11-24) asked 87 questions of six banks on seven page states with every page set up. Before the fixes in this record it raised seven false alarms, each traced to a cause: a fold's table read as one string ran its numbers together ("74", "12.85", "233.5" read as 7412.85233), a sweep's and a solve's first answer were replaced by their result, a yes-or-no question quoted the bank example's 16,220 N where this coupon gives 16,210 N, the customer's setup screen and spar caps differ from the bank's examples, and a question asked before the setup's preview arrived was answered otherwise than one asked after it (the robot now waits for the page to settle). The first four have tests in `tests/site-check.test.ts`.
- The same run found what checks 1 and 2 cannot see, each confirmed by the picture of the chat: on the customer's setup screen, with "Everything is stated" and the geometry "from the standard", "how wide is it?" is answered "No width yet" (criteria 2 and 9); after "solve the slice" on the repair, the answer's heading is 69 characters (criterion 8); once a sweep with no quantity named is worked, the answer no longer says that the step length was taken for it and how to sweep another (criterion 2). These are reported, not fixed, here.
- `npx tsx --test tests/site-check.test.ts`: 16 passed. `cd api && uv run pytest tests/test_model_costs.py`: 12 passed, 5 skipped.
- The cost of a full run on the hosted site is not measured yet: no run has reached anisotropy.dev, since the token is a repository secret that only the workflow holds. UNVERIFIED until the first run; the cap holds it to $1 whatever the measure.

## Consequences

- An answer that goes wrong on the live site is found within a deploy for the page's own answers and within four days for the model's, without anyone asking.
- The banks now serve three checks. A question whose expected words hold only for the bank's fixture shows up as a mismatch on the live site; the fix is in the bank or in `LIVE_DIFFERS`, never in loosening the check.
- A number that traces by coincidence to some value of thousands the result's field holds passes the number check: it catches numbers that come from nowhere, not every wrong one. The judge is told not to grade numbers.
- Each run solves one coupon through the queue, under the actor `test`, and counts against the daily cap of jobs with no email, as the deploy check does.
- Invented questions (an agent that writes new questions each full run and proposes the ones that fail for the banks, by pull request) are left for a later amendment.

## How we will know it was wrong

- More than one issue in a month that the founder closes as a false alarm: the fixed checks or the judge are too strict, and the record is amended.
- An answer the founder finds poor on the live site that a full run asked within the four days before and passed.
- A month whose spend passes $20, or a run that passes $1.
- Any secret, email address or signed link found in a run's log, summary, artifact or issue: the run's output is taken down and the robot stops until it is fixed.

## Amendment 1, 2026-11-24 (the first live run: the version check asked through the page, no crash on a closed page, every printed line scrubbed)

**Context.** The first run on anisotropy.dev (Site check run 45492884547, after the deploy of 07ac0fe) set up no page. The robot read the site's version with Playwright's own request context, which does not pass through the context's route and so carried no Access headers: Access answered with its sign-in page, and reading that as JSON ("Unexpected token '<'") marked every page as not set up. A page was then closed while a job's file was being fetched, the route's handler failed ("Request context disposed"), and Node printed the error, with the bucket's signed link to that file, into the run's public log. The link had expired (600 s) when it was found; it also named the bucket's account host. By the rule of "How we will know it was wrong", the run's logs were deleted the same hour (204 from GitHub), its upload step had not run, and no run has followed.

**Options.** (a) Add the token's headers to the request context too: the token would then travel on a second path, which is what the safety rule keeps to one. Rejected. (b) Ask the version from the page, by its own `fetch`, so it passes the route as the page's requests do; catch every failure inside the route's handler and drop the request; scrub every line the robot prints, and print an uncaught error scrubbed rather than let Node print it. Chosen.

**Decision.** (b), under the founder's rule that the robot "needs to be safe". `run.ts` asks `/api/version` by `page.evaluate(fetch)`; the route's handler aborts a request it cannot finish and prints nothing; `console.log`, `console.error` and `console.warn` pass through `scrub` with the run's secrets, and `unhandledRejection` and `uncaughtException` go through the same. `scrub.ts` also hides the bucket's host (`*.r2.cloudflarestorage.com` becomes `[storage]`), so a link's path may be printed but never its account or its query.

**Evidence.** `npx tsx --test tests/site-check.test.ts`: 16 passed, the scrubbing test now holding the shape the crash printed (host, `X-Amz-Credential`, `X-Amz-Signature`). `npx tsc --noEmit -p .`: clean. That the version check passes Access on the live site is UNVERIFIED until the next run.

## Amendment 2, 2026-11-25 (the second run: the deployed commit's banks, a run that tells nothing when the site changes under it, no spend in a quick run, the store kept as an artifact, one comment per new failure)

**Context.** The second run (Site check run 45534267772, after the deploy of 29d483b) asked 256 questions with every page set up, wrote no secret to its log, and opened issue #275 with 81 answers that fail. Most of them say more about the run than about the site. (1) A run after a deploy checks out main, which had moved on: the banks were of 1d64514 (the misuse bank of ADR-0139) and the site of 29d483b. (2) The deploy of 1d64514 landed while it asked (02:45 to 02:54 UTC): every answer in that window was missing or "could not answer right now". (3) A quick run is to spend nothing on the site, and it spent $0.37: the page sent to the model questions its banks say the page answers itself. (4) The grades, the month's spend and what failed were not kept: GitHub gives a run started by another workflow's run a cache it may read but not write ("cache write denied: token has no writable scopes"), so the month's cap of $20 could not be held. (5) Three kinds of answer are misread by the robot: an answer shown with the page still at work under it ("Got it, units: in, psi and lbf", then "Checking the setup…" past 45 s) counted as no answer; a question typed while the site's solvers were busy with the last one's check was answered "unavailable", which no engineer typing at a person's pace sees; and a bank's question of a page without the Ansys file, which the site offers to everyone (ADR-0129 amendment 3), failed for offering it. (6) An open issue gains a comment from every failed run, so a failure that stays would write to the founder after every deploy. (7) A page is set up once for all its questions, so "what units are you using?" was asked after "work in metres" and failed for answering "m, Pa and N", which was right.

**Options.** For (1) and (2): cancel a run when a newer deploy starts (runs then rarely finish on a day of many merges), or ask the deployed commit's banks and leave out a run whose site changed. The second is chosen. For (4): `actions: write` on the job that grades (it would also let that job cancel runs and delete logs, and may not lift the read-only cache of such a run), or keep the store as an artifact the next run fetches with `actions: read`. The second is chosen. For (3): mark more questions in the banks as the model's (the next change to the page would undo it), or have the robot refuse the model's routes in a quick run. The second is chosen, since it holds whatever the banks say.

**Decision.**
- A run asks the banks of the commit the site runs: after a deploy, the workflow checks out that deploy's commit and passes it as `--expect`. The robot reads the site's commit from `/api/version` in a page of its own (which replaces amendment 1's read from the first page set up), waits up to five minutes for the site to take up the deploy, and asks nothing if the site runs another commit. It reads the commit again at the end; if it changed, the run tells nothing: no issue is opened, added to or closed, and what failed before is kept.
- In a quick run the robot answers the page's calls to the model's routes itself with "unavailable", so nothing reaches the site's model. A question the page sent there is left for the full run and named in the report, as a bank whose route differs from the site.
- The store (`ledger.json`, `last-asked.json`, `failing.json`, the judge's grades) is the artifact `site-check-store`, kept 90 days; a first job finds the last one with `actions: read` and the next run fetches it. How long a grade has gone unused is kept in `grades-used.json`, not in file times, which an artifact need not keep.
- An answer shown with the page still at work under it is graded as that answer, timed from when it was shown, and weak with what the page was still doing. After each answer the robot waits up to 90 s for the page's requests for work (not its reads) to finish before the next question. A question that starts a run waits up to five minutes.
- A bank's question of a page without the Ansys file is left out when the same bank asks the same words with the file offered.
- A question whose answer changes the page's rows at once (the routes `patterns` and `name`: "switch to inches", a name) has the page set up again after it, as a question that moves the page on does.
- An open issue gains a comment only when something fails that did not in the run before (`newlyFailing`); a page not set up counts as `page:<name>`.

**Evidence.** The second run's log (no signed link, bucket host, address or token in it) and issue #275. Of its failures, two were the site's: "switch to inches" and "show all the rows" on the tension screen, fixed by ADR-0090 amendment 2. `npx tsx --test tests/site-check.test.ts`: 19 passed. Quick runs on this machine against main (4f0630f) served locally: the units and downloads banks asked 36 questions, then the downloads bank alone 17, with $0 spent on the site's model; the Ansys twins were left out, and "switch to inches" was graded weak with "Checking the setup…" instead of no answer. The first of them lost its answers at the end: this machine ran out of memory under the inches check, the browser closed, and the closing read of the commit threw; that read now gives no commit instead. The local site serves no `/api/version`, so the commit check was not tried there. That the commit check, the artifact store and the deployed-commit checkout work on GitHub is UNVERIFIED until the next run.

## Amendment 3, 2026-11-25 (the third run: a quick run starts no analysis, the robot keeps no project on the site, "run" answered in the page's own words, the bond's page set up)

**Context.** The third run (Site check run 45552826102, after the deploy of 2dbcf8f) confirmed amendment 2 on GitHub: it checked out 2dbcf8f and passed it as `--expect`, the site answered with that commit, the quick run spent $0.000 on the site's model ("Asked 143"), the judge $0.033, "what units are you using?" held once the page was set up again after "work in metres", and the store was saved as the artifact `site-check-store` (137 files). No earlier store artifact existed, so fetching one is still to be seen in the next run. It showed four more faults. (1) The deploy check of the same deploy ran no coupon job: "the day's cap for the check's jobs is reached". The deploy check and the robot sign in with the same service token and actor `test`, so they share one person's daily analyses (ADR-0056), and every quick run started some: the page of results, "run", "solve" and "run it". (2) "run" and "solve" waited 300 s each and were reported "no answer appeared": the page writes the engineer's "run" as "Run the analysis", and the robot looked for the words typed. Asked locally with the day's analyses used up, the page answered "The analysis could not start" with the reason. (3) The wing's spar-cap page could not be set up and "is the spar cap laminate balanced?" was answered of a wing with caps: a page with no project of its own in the browser opens the newest one the site keeps for the sign-in (`useNewestFromServer`), and an earlier run's setup had added caps to its wing, which the site kept. Seeded the same way locally, a fresh browser opened the wing with caps. (4) The bond's page (ADR-0140) had no setup, so its questions were never asked.

**Options.** For (1): a sign-in of the robot's own with its own count (a second service token and an API change), or a quick run that starts no analysis, leaving the run of a job to the deploy check after each deploy and the robot's full run every four days. The second is chosen: a quick run already spends nothing on the site, and the deploy check is what proves a job end to end. For (3): delete the robot's kept projects before each run (a write to the site's database from a public workflow), or answer the projects as an API that keeps none. The second is chosen: each run starts as a new customer and writes nothing.

**Decision.**
- In a quick run the robot answers a request that starts an analysis (`POST /v1/coupon-jobs`, `POST /v1/wings/checks`) "unavailable" itself, as it does the model's routes; a question that started one is left for the full run and named in the report. A quick run asks no question of the route `run` and sets up no page of results.
- In every run the robot answers the site's projects (`/v1/projects`) as an API that keeps none (503, `X-Anisotropy-Records: off`), so a page opens the example and nothing is kept (`scripts/site-check/routes.ts`).
- The engineer's message is the one written in the words typed or, where the page writes it in its own words, the first written after it was sent.
- The bond's page is the example repair solved, then its bond followed on "Follow the bond".
- The site's one fault found by the judge that was a slip of words, "A coupon's are set by its test", now names the boundary conditions in the glossary of FEA words (`lib/fea-terms.ts`); the chat's note with the same slip was rewritten meanwhile by ADR-0089 amendment 8.

**Evidence.** The third run's logs (no secret, signed link or address in them) and its comment on issue #275; the Deploy run 45551730445's check: "The coupon job was not run: the day's cap for the check's jobs is reached." `npx tsx --test tests/site-check.test.ts`: 20 passed. On this machine, the site built with its API at `/api` as on the hosted tier and served with a local API whose day's cap was used up (one job a day, one job filed): a quick run of the wing, units and repair banks set up every page, wing, spar caps and bond included, asked 93 questions and left "run it" for the full run; a full run of the units bank read "The analysis could not start" for "run" and "solve". That the hosted deploy check runs its job again on a day of quick runs is UNVERIFIED until the next deploy.

## Amendment 4, 2026-11-26 (the planner asked in a full run, on a project of the page's own kept on the site, and never approved)

**Context.** The workspace's planner (ADR-0144) plans only on a kept project, and amendment 3 answers the site's projects as an API that keeps none, so the robot could not ask the planner at all. An approval starts an analysis and counts against the sign-in's daily analyses; a plan calls the model and counts against its 30 planned requests a day.

**Options.** Leave the planner out of the site check: rejected, since the planner is the feature most in need of a check on the real site. Ask it in every run: rejected, since a quick run spends nothing and keeps nothing. Ask a few in each full run on a project of the page's own, never approving: chosen, pending the founder's word, because it writes to the site's database, which amendment 3 chose not to do.

**Decision.** In a full run, at most three planner questions (`PLANS_PER_RUN`), those asked longest ago first, on the setup and ready pages only (setting up the page of results starts an analysis). Each gets a browser of its own in which the page's own project is saved and read back by its id (the project list is still answered as none), so the site can plan on it. The robot answers every approval, step report and run itself (409, or "unavailable"), so none reaches the site; a card past its approval fails the question. The card's state, steps and reason or question are graded by the plan's contract and the bank's `live.plan`; the judge is told a plan waits for approval. A site with no planner (the project not kept, the route 404 or 503, or the plan `unavailable`) leaves the question for a later run. A quick run asks no plan. The projects stay in the site's database under the check's service token, up to three a full run; there is no route to delete them. Drafted by Claude Code; awaits the founder's word on keeping them.

**Evidence.** `npx tsx --test tests/site-check.test.ts`: 24 passed, among them that every one of the 25 planner questions a site can be asked comes up within nine full runs. The cost per full run is estimated, not measured: about $0.03 a plan, $0.10 to $0.20 for three, at most about $0.60, inside the run's $1 cap.
