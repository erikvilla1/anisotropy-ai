## Context

A question typed in the workspace chat is answered by one of three kinds of reader: the page's own patterns (ADR-0099, ADR-0110), a model behind the API that reads it into proposals, a typed question of the results or an answer in words (ADR-0088, ADR-0100, ADR-0101, ADR-0102), or, from an MCP client, the client's model with our tools (ADR-0107). Each reader had its own tests, but nothing asked the questions a user types, in the many ways they type them, across the readers together. On 2026-11-17 four of ten questions the founder asked on the hosted site got a poor answer though every number was right (the `chat-answer-quality` skill). The chat chose its reader inside the component's `send()`, so the choice could be tried only in a browser.

## Options considered

1. **A browser test per question.** Tries the real component, but a few hundred questions at seconds each would slow every pull request, and a browser test cannot reach a real model. Rejected.
2. **A review on the hosted site after each feature** (the skill's procedure). Sees the real thing, but needs the founder's time and his key, one page state at a time, and is not repeated. Kept for live reviews, not as the check.
3. **A real model on every pull request.** Catches what only a model gets wrong, but costs on every push, its answers vary from run to run, so a check would fail at random, and a pull request from a fork gets no secret. Rejected; the founder chose a run before each feature merges.
4. **Question banks as data, three checks.** The questions and what a good answer holds are written once per feature; free checks hold the page, the API and the MCP server to them on every pull request; a real-model run reads the rest before a feature merges; and a pull request that changes the assistant brings its questions. Chosen.

For the real-model run's place the founder was offered every pull request, weekly and before merges, before each feature merge, and only on his PC; he chose before each feature merge. For its cost, running every question at full price each time was set against storing answers and the levers below.

## Decision

1. **Banks.** One JSON file per feature in `tests/assistant-questions/`, its fields described in `harness.ts`. A question holds its words, its kind (value, which, yes-no, what-is, why, change, command, off-topic), how it is typed (plain, typo, fragment, loose, jargon, units, terse), the page it is asked on, who answers it with a model and without, and what the answer holds (`answer`), the theory sections a why question finds (`sections`), the MCP tool that answers it (`mcp`) and what a model should make of it (`live`). Each bank asks ten questions or more, of two kinds or more, in three styles or more, one with a typo. A bank names the files it watches. A bank written before its feature (`waiting`) holds the questions the feature must answer; the wing's waits for draft PR #244.
2. **Known gaps fail when they close.** A question whose answer is known to be poor carries `gap`, with the criterion it fails. Its check expects the fault, and fails once the fault is gone, so the mark comes off with the fix.
3. **The chat's choice of reader is a function**, `routeMessage` in `lib/chat-route.ts`, which the component calls and the banks call.
4. **Check 1, on every pull request, free, in the jobs that exist.** `tests/assistant-questions.test.ts` routes each question with a model and without and holds the page's answer to its bank and to the rules every answer keeps (a question never changes the setup, no name of a tool, vendor or model, a heading of 60 characters at most); every way the chat answers is taken by some question. `api/tests/test_assistant_questions.py` holds each why question to the theory sections a model is shown, and maps every `/v1/workspace/` route to the questions that reach it. `mcp-server/tests/test_questions.py` puts each MCP question to its tool and asks every tool about.
5. **Check 3, on every pull request.** `scripts/assistant-questions-check.mjs` (workflow "Assistant questions") fails a pull request that changes a file of the assistant or one a bank watches and changes no bank, unless its description has a line "Assistant questions: none needed" with the reason.
6. **Check 2, a real model, by hand before a feature merges.** The workflow "Assistant check" runs `scripts/assistant-live.py`: each question a model reads is sent as the page sends it (`requests.ts`) to the API's own readers in process, with their instructions and guards, on `claude-opus-5-5`, the site's model; the page's answer is drawn from what they return (`shown.ts`) and held to `live`; `claude-haiku-5-5` grades, against the skill's eleven criteria, each answer a bank describes in words and each answer of why; `scripts/assistant-live-mcp.py` puts each MCP question to `claude-sonnet-5-5`, standing in for an engineer's own assistant, with the server's tools and instructions, the server answering in process from the stored results. The report goes on the run's page, feature by feature, with what changed since the last run, and the run fails when an answer that held now fails. The agent that built a feature starts the run before it calls the pull request ready, within the budget.
7. **What keeps check 2 cheap.** An answer is kept under the exact request (model, instructions, schema, words), between runs as the run's artifact, so a run pays only for what changed; the rest go in one batch at half price, with the instructions marked for the prompt cache; the judge is the small model; a run stops before it would pass its budget (3 dollars unless given), and `--dry-run` says what a run would send. A batch carries no fallback to another model on a decline, which the site's requests carry.

## Why (evidence)

- The checks pass on the branch, with the gaps held: `npx tsx --test tests/assistant-questions.test.ts` 17 of 17; `cd api && uv run pytest tests/test_assistant_questions.py` 16 passed; `cd mcp-server && uv run pytest tests/test_questions.py` 15 passed.
- The routing moved without a change in behaviour: the studio's browser suite, 56 of 56, after the move.
- The banks found what the existing tests did not, among the 45 gaps: a typo of "stress" is not read with no model; "which ply fails first by max stress" gets a table of stresses; "how did you get 16740 N" sets a load of 16740 N; "what is ASTM D3039" changes the setup; a yes-or-no question about a result does not open with Yes or No; "can I use inches?" switches the units.
- The real-model run was run end to end against a stand-in for the Messages and Batches API on this machine, with no model and no cost: four features, 81 requests the first time, none the second (all from the store), an answer made to fail after holding failed the run, and a budget of 5 cents stopped it before anything was sent.
- `--dry-run` on all banks: 99 questions for the API's readers and 14 for an MCP client; the readers' first requests about 1.43 dollars on the high side at batch prices. Prices from the claude-api reference (2026-11-19).
- UNVERIFIED: no run against the real model yet (the secret is not set); what a full run and a feature's run cost is not measured.

## Consequences

- A feature that changes the assistant lands with the questions a user would ask of it, and a known poor answer is listed until it is fixed.
- A pull request that changes the assistant writes questions, or a line saying why none are needed.
- The banks' harness draws the page's answers with the page's own functions, but it repeats how the component puts them together; a change to the component can leave it behind. The browser suite still tries the component.
- Check 2 depends on a repository secret, the Batches API and the stored results in `tests/fixtures/`.

## How we will know it was wrong

- A question asked on the hosted site gets an answer its bank holds as good: the harness has drifted from the page.
- A feature's run of check 2 costs more than 5 dollars, or its verdicts change on answers that did not.
- Most pull requests that change the assistant say "none needed": the rule is noise. Look again after ten such pull requests.

## Amendment 1, 2026-11-20 (a fast switch; requests and conversations sent at the same time)

**Context.** The founder asked, while the first real run waited on its batch: "is it not possible to deploy multiple agents at the same time ... instead of just one by one" (2026-11-19, 5:52 PM PT). The readers' questions already went in one batch, answered side by side, but a batch is answered when the provider has room (most within minutes, at most 24 hours), and two parts went one at a time: the full-price path (`--now`) and the fourteen MCP conversations.

**Options.** (1) Keep the batch alone: the report waits on the batch queue. Rejected. (2) Always send at once at full price: about twice the cost of every first run. Rejected as the default. (3) An agent with a browser per question: no browser is needed, the banks' harness calls the chat's own functions, and the browser suites already run in parallel. Rejected. (4) The batch stays the default; a "fast" input on the Run button (`--now`) sends every request at once at full price, eight at a time; the MCP conversations always go on eight at a time, each conversation's turns still in order; requests sent together reserve their estimate first, so together they cannot pass the budget. Chosen.

**Decision.** Option 4: `AT_ONCE = 8` in `scripts/assistant_live_common.py`, `talk_all` in `scripts/assistant-live-mcp.py`, the input `fast` in `.github/workflows/assistant-live.yml`.

**Evidence.** Against the stand-in for the Messages API with each answer held back one second, on every bank: a whole fast run took 202.7 s before and 33.2 s after, with the same report; the MCP half 30.4 s before and 6.2 s after, with the same answers; a rerun sent nothing and answered 195 requests from the store; a budget of 5 cents stopped a fast run with nothing sent. The readers' first requests at full price: about 2.86 dollars on the high side (`--dry-run --now`). What a real fast run costs and takes: UNVERIFIED.

## Amendment 2, 2026-11-20 (a question is answered, or said so, and never read into rows)

**Context.** The first real-model run (run 44654876004, 2026-11-20: 113 answers graded, 61 hold, 19 weak, 33 fail) found the commonest fault was the chat treating a question as a change. Asked "what units are you using?", "is it ready to run?", "who made you" or "what do I need to set up a coupon", it answered "Not sure what to change" with three example values; asked "can I use inches?" it switched the units and cleared the sizes; asked "what is a tension coupon", "what is ASTM D3039" or "how did you get 16740 N", it set the test, the standard, or a load of 16740 N. Each of the last was a question changing the setup (criterion 1 of the `chat-answer-quality` skill).

**Options.** (1) Leave these to the model: a model read most of them on the hosted site and still proposed the change, and the page needs no model to say its own units. Rejected. (2) Teach the setup's patterns to skip question words: they would still have nothing to answer with. Rejected alone. (3) Two routes of fixed words before any reader that changes rows, and a question nothing reads said so: `about` for who the assistant is, what it can do, its units, whether another unit system or a material of one's own is offered, which layup (the common ones offered, none chosen), what a coupon needs, whether von Mises suits a ply and another program named, all in `lib/chat-about.ts`; `ready` for whether the setup is ready, answered by the setup check with a heading that opens "Yes, ready to run" or "No: N things to fix before running"; the glossary takes the names of the tension test, ASTM D3039 and the 10% rule (ADR-0110), with a word that has nothing of the model's own (`general`) asked about as "what is the 10% rule"; "run it" before the setup is ready, and "chekc", check the setup; the working is asked by a question even when it holds a number; and anywhere a message that opens as a question (`isQuestion`) and that nothing read is told what can be asked, with the setup's examples when no result is shown. Chosen.

**Decision.** Option 3: `lib/chat-about.ts`, the routes `about` and `ready` in `lib/chat-route.ts`, `answerAbout` and the asked check in `components/studio/coupon-chat.tsx`. No answer names a model, a vendor or a tool: "who made you" is answered "Anisotropy's assistant", and "can you run this in abaqus" says it is solved here, pointing to the card that sends the coupon to the engineer's own copy, without naming it. "help" keeps the pointer to the next thing to state.

**Evidence.** The banks: 18 questions moved from a model or the patterns to these routes and the glossary, 8 known gaps closed and their marks taken off, and 7 questions added (224 questions, 37 gaps open) (`npx tsx --test tests/assistant-questions.test.ts`, 17 of 17 pass); a browser spec asks "can I use inches?", "what units are you using?", "who made you", "what is a tension coupon", "is my setup ok?" and "how did you get 16740 N" on the page and checks nothing was changed or sent (`tests/browser/studio.spec.ts`). These questions no longer go to a model, so the real-model run sends fewer requests; what the next run grades: UNVERIFIED until it runs.

## Amendment 3, 2026-11-20 (what the judge of an MCP answer is shown, and what counts as the bank's call)

**Context.** Of the MCP conversations in the first real run (run 44654876004), four were failed by the check and not by the answer: "where is the shear stress highest?" left `sense` at the tool's default, `magnitude`, which the bank named; "why is ply 4 in compression?" passed the question in the model's own words; "stress at element 9999" was answered without a call, rightly, from the 250 elements the solve had already reported; "run a 250 x 25 IM7/8552 [45/0/-45/90]s coupon at 1 mm" asked for the rows still missing, as the server's rules say, where the bank expected a solve. The judge also failed numbers the tools had written (the load at first-ply failure, 17150 N, is the working's own line) because it was shown the calls and not what they returned. And the stand-in API answered a material's values with E1 alone, so "what are the allowables for IM7/8552" could not find the strengths the API holds.

**Options.** (1) Loosen each bank row by hand. Rejected alone: the next tool with a default would fail the same way. (2) Match a call by the tool's own schema: an argument left out counts as its default, a free-worded argument (`question`) counts when given, and a question the bank expects refused, answered without a call, counts when the answer says what the bank says; show the judge what every tool returned, the context's solve included, cut at 9,000 characters each; answer `material_values` with the API's own answer, kept equal to it by a test of the API. Chosen, with the one row whose expectation was wrong rewritten: the coupon with no tabs asks for what is missing.

**Decision.** Option 2: `called_as_asked` and `shown` in `scripts/assistant-live-mcp.py`, the judge's item in `scripts/assistant-live.py`, `mcp-server/tests/fixtures/material-im7-8552.json` with `test_the_mcp_servers_stand_in_answers_with_this_apis_own_material` in `api/tests/test_library_api.py`.

**Evidence.** Against the stand-in for the Messages API (no key, no cost), four banks ran end to end with the MCP half: every call carried what it returned and the judge's request carried the context's solve. The matching rule tried on its own: `sense` left out matched the bank's `magnitude` and `largest` did not; a reworded why matched; a refusal without a call matched only when the answer said "1 to 250". What a real run grades after it: UNVERIFIED until it runs.

## Amendment 4, 2026-11-20 (a value of the setup asked for; what the second run's judge could not see)

**Context.** The second real-model run (run 44663842680, 2026-11-20, $0.68: 89 answers graded, 56 hold, 11 weak, 22 fail, against 61, 19 and 33 of 113 in the first) found four faults that were not the assistant's answers. "what is the width?" on a setup went to a model that proposes changes and was answered "Not sure what to change", where the width is on the page. The judge failed "is my setup ok?" asked of an MCP client for naming who filled the coupon in, because it was not shown that the engineer had said so before asking; it called the product's own name a vendor's. Asked why, the MCP client found only the stand-in API's one fixed section, so it could not answer from our pages. And four bank rows expected the wrong thing: "pull it 2 mm" and "displacement 2 mm" a proposal of `value`, where the row a model proposes is `displacement` (the page then fills the loading type and its value); "run a 250 x 25 IM7/8552 [45/0/-45/90]s coupon at 1 mm" a list of rows that fitted only the MCP client; "is ply 2 above 1000 MPa?" the gauge centre's 1182 MPa alone, where the largest, 1203 MPa with its place, answers it as well.

**Options.** (1) A value of the setup sent to a model: the page holds it, and no model may type a number (ADR-0001). Rejected. (2) A topic of `about` that reads the setup's own row: "what is the width?", "how wide is it?", "what's the layup", "what material is it?" answered "Width: 25 mm", "Layup: [45/0/-45/90]s" in the setup's units, or "No width yet"; only a short question that names a row and nothing else, so "what is the width of the stress" and "what are tabs?" are not read; never on a past run or an imported model, where the rows are not the model. Chosen. With it: the judge shown what the engineer told the MCP client before the question, and told the product's name; the MCP half searching our theory pages with the API's own `theory.py` (which reads only the documents); the four rows rewritten to what a good answer holds.

**Decision.** Option 2: `setupRowAsked` and the topic `setup-value` in `lib/chat-about.ts`; `TheoryApi` and `before` in `scripts/assistant-live-mcp.py`; the judge's item and instruction in `scripts/assistant-live.py`; the rows in `tests/assistant-questions/coupon-setup.json`, `which-ply-fails.json`, `result-values.json` and `off-topic-and-safety.json`, with three questions of a setup's value added.

**Evidence.** `npx tsx --test tests/assistant-questions.test.ts` 18 of 18 pass (2026-11-20), and fails when the expected width is changed to 26 mm; the browser spec of amendment 2 asks "what is the width?" and finds "Width: 25 mm" with nothing changed; the theory search of the MCP half, asked "why does ply 4 fail first", found "Why a 90-degree ply usually fails first in a tension coupon" and "7. First-ply failure". What the next real run grades: UNVERIFIED until it runs.

## Amendment 5, 2026-11-20 (the third run's last failures)

**Context.** The third real-model run (run 44666716192, 2026-11-20, $0.21: 93 answers graded, 60 hold, 26 weak, 7 fail) left seven failures. Three were the assistant's: "change ply 3 to 30 degrees" was read into nothing, since no row on offer held one ply's angle (a model may only fill a row the page offers, ADR-0088, and the layup's notation must be written in the message); "what is the ABD matrix?" asked on a coupon's setup was answered "Not a question I can answer yet", where FEA's own assistant answers the same question in words before a setup (ADR-0124); and an MCP client asked about element 9999 said the range and then asked which ply and which stress, and asked for the Tsai-Wu working it asked which criterion to show, where the page takes its defaults (criterion 2 of the `chat-answer-quality` skill). Eleven of the 26 weak answers were answers of why that did not say where the result is read (criterion 5). One failure is left as it stands: "where does the 90 ply see the most tension" was read as σ₁ and σ₂, where the tension a 90-degree ply sees in this coupon is σ₂ alone; the answer shown is right (σ₁ all in compression, σ₂ at 60.6 MPa) and the bank keeps σ₂ as the reading to aim for. Two remain known gaps of our theory pages: when a hand calculation is enough, and why the shear stress is zero in the 0 and 90 degree plies.

**Options.** (1) Leave the ply's angle to the layup's notation: an engineer changing one ply would retype all of them. Rejected. (2) Offer each stated ply's angle as a row of its own kind, `angle`, in degrees from -90 to 90, its written unit checked and dropped by the guard, and read "change ply 3 to 30 degrees", "ply 2 = -45°" and "ply 6" of a symmetric eight by the page's own patterns too, a symmetric layup's mirror changing with it. Chosen. (3) Send a question of meaning on a setup to the model that proposes rows: it proposes none and the page says it could not read it. Rejected. (4) Answer it as FEA's own assistant does, by the theory pages' reader of ADR-0124, with no kind of work offered since the coupon is set up: the first sentence as the heading and the sections under Details, as an answer of why. Chosen, only with no result on the page (with one, a question is read as one of the results, ADR-0100) and only for a question with no number in it. (5) The MCP client's rule 11: a question that leaves out the ply or the quantity means every ply and σ₁, σ₂, τ₁₂; an element not in the model gets its range and the values where first ply failure is read; a working the result does not have gets the one that fails first. Chosen. (6) The why answer's small line says where the result is read, from the fact sheet's `basis` ("Read in the gauge section."). Chosen.

**Decision.** Options 2, 4, 5 and 6: `readPlyAngle` in `lib/studio-chat.ts` and the `angle` rows of `couponOffer` in `lib/proposals.ts` with the guard's `angle` kind in `api/src/anisotropy_api/proposals.py` and `schemas.py` (ADR-0088 amendment 3); the route `general` in `lib/chat-route.ts` and `answerMeaning` in `components/studio/coupon-chat.tsx`, with the first sentence of a general answer asked for in at most nine words (`GENERAL_SYSTEM`); rule 11 of `INSTRUCTIONS` in `mcp-server/src/anisotropy_mcp/server.py` (ADR-0107 amendment 2); `readAt` and the note of `whyLines` in `lib/result-why.ts` (ADR-0102 amendment 3). The banks: the ply's gap closed, "what is the ABD matrix?" routed `general`, and "what does tsai-hill mean" and "explain first ply failure" asked on a setup.

**Evidence.** `npx tsx --test tests/assistant-questions.test.ts` 18 of 18, `tests/studio-chat.test.ts`, `tests/proposals.test.ts` and `tests/result-why.test.ts` pass; `cd api && uv run pytest -q tests/test_proposals.py tests/test_result_answers.py tests/test_assistant_questions.py tests/test_general_answers.py` 127 passed, 4 skipped; `cd mcp-server && uv run pytest -q` 54 passed (2026-11-20). `npm test` 458 passed, 1 skipped.
