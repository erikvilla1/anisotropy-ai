## Context

- ADR-0027 names two tiers: a hosted tier run by us for students, professors, research groups and small shops working with public data, where the assistant is a main feature, and a self-hosted tier for regulated customers. ADR-0025 left the hosting of the run records "decided at deployment". Today the API and the solvers run on the founder's machine only (ADR-0050, Consequences). The founder has asked that engineers and invited users open the website, sign in with their email, and take a coupon from the chat to its package with nothing installed, every solver running on our side (the browser release plan, 2026-10-30).
- The site is a static export (`output: "export"` in `next.config.ts`). Each page reads the API address at build from `NEXT_PUBLIC_ANISOTROPY_API_URL` and prefixes it to `/v1/...` (`app/studio/page.tsx`, `lib/studio-api.ts`), so a path on the site's own origin such as `/api` is a valid address, and no server rendering is used.
- The API is FastAPI with no authentication (ADR-0011); its actor header is a label, not an identity (ADR-0026); its CORS list is four loopback origins in `main.py`. A coupon job runs `uv run --project fea python fea/tools/run_coupon.py` in a background thread, one job at a time, its status in memory and its folder under a temporary root (`coupon_jobs.py`, ADR-0050); the coupons live under `.local/fea/<coupon>/` (`fea/src/anisotropy_fea/paths.py`). A job with the PDF took 80 s on the founder's machine (ADR-0050, evidence).
- The job needs programs, not only Python packages: CalculiX (the reference solver), Gmsh (the `mesh` extra, which needs libGLU) and Tectonic (the PDF). CI installs `calculix-ccx` and `libglu1-mesa` with apt and downloads Tectonic 0.17.0 (`.github/workflows/tests.yml`). Abaqus is optional and runs on a UCSD teaching licence (ADR-0045).
- Run records are PostgreSQL through one `DATABASE_URL`, with Alembic migrations 0001 to 0004 (ADR-0025, ADR-0026). The assistant is off unless a provider, a model and a credential are set (ADR-0052). A feature of one tier must be a setting, not a fork (ADR-0027), and nothing is defaulted silently (ADR-0003).
- Nothing in the repository has faced the internet. Nothing private may enter the repository or an image built from it (ADR-0042).

## Options considered

Where the site, the API and the solvers run:

1. **Vercel.** Static hosting with Next.js server features the export does not use. Functions run at most 800 s on Pro (1,800 s in beta) with 4 GB and 2 vCPU and a 500 MB Python bundle, and hold no CalculiX or Tectonic. Sandbox runs a custom image (8 vCPU, 16 GB and 24-hour sessions on Pro) at $0.128 per active CPU hour plus $0.0212 per GB-hour, is built for untrusted code, and does not run the image's `ENTRYPOINT` or `CMD`. Hobby is for non-commercial, personal use only; Pro is a $20 a month platform fee; Blob egress is billed. Rejected: the solver needs a container, and the platform's strength goes unused.
2. **Cloudflare.** Static asset requests are free and unlimited; Workers Paid is $5 a month. Containers run any Docker image on instance types up to 4 vCPU, 12 GiB and 20 GB of disk (`standard-4`), 1,500 vCPU and 6 TiB per account at once, billed per 10 ms while running and scaled to zero when idle. R2 holds files with no egress charge. Access signs users in with an email allow list and one-time PINs, with no identity provider. Queues are there for a job queue later. Chosen.
3. **AWS now** (a container service, S3, a load balancer with sign-in, managed PostgreSQL). More parts to set up and a monthly floor before the first user; what it offers (GovCloud for a regulated customer, larger machines, credits) is not needed for an invite-only beta. Deferred by the founder to when one of those appears. Cost comparison: no evidence yet.
4. **Supabase** for sign-in, files and PostgreSQL beside another host. Overlaps Access, R2 and the FastAPI API, so two vendors would do one job. Rejected.
5. **Google Cloud Run Jobs**: 8 vCPU and 32 GiB per instance and a task timeout of 7 days. Kept as the place for a job that outgrows a Cloudflare container; the same image runs there.

How the solvers reach a browser user:

1. **In the browser.** Our kernel is numpy and scipy, which Pyodide can run; CalculiX, Gmsh and Tectonic cannot run there. Kept as a later idea for an instant preview, not as the product.
2. **On serverless functions.** Neither platform runs native programs there (options 1 and 2 above).
3. **One Docker image** holding Python 3.12, uv, the engine, api and fea packages, CalculiX, Gmsh and Tectonic with its TeX bundle cached at build, started as the API container and later as one solver container per job. Plain Docker with nothing Cloudflare-specific inside, so the same image runs on Cloud Run, on AWS, and as ADR-0027's self-hosted delivery. Chosen. Abaqus is never in the image or the hosted product; the `.inp` decks stay downloadable for users with their own licence.

Sign-in:

1. **Our own sign-in code** (users, passwords or OAuth, sessions). Code to write, test and secure before the first invited user; ADR-0027 scheduled authentication for the first proprietary customer.
2. **Cloudflare Access in front of the site and the API**, with an email allow list and one-time PIN login and no public sign-up. When its settings are present, the API accepts only requests that carry Access's signed token (`Cf-Access-Jwt-Assertion`) and records the signed-in email on run records and jobs; without them, nothing changes locally. Chosen.

The database:

1. **PostgreSQL in the container**, as `docker-compose.yml` runs it locally. The container's disk is ephemeral. Rejected.
2. **Neon**, hosted PostgreSQL: a changed `DATABASE_URL` and nothing else (ADR-0025); scales to zero after five idle minutes; a branch is a copy-on-write copy for a preview; SSL required. Chosen. Any managed PostgreSQL would serve the same way; the code depends on nothing Neon-specific.
3. **Cloudflare D1**: SQLite, which ADR-0025 rejected because tests would run against something other than what is deployed; the migrations use JSONB. Rejected.

Job outputs and status:

1. **The container's disk and the job dictionary in memory**, as today. Both vanish when the container sleeps or is redeployed. Rejected for the hosted tier.
2. **R2 through its S3-compatible API for the files, and a `jobs` table for the status**, used only when their settings are present; the local disk and the in-memory status otherwise. Chosen. Run records stay immutable (ADR-0026); only the jobs row changes state.

How many jobs at once:

1. **A queue with one container per job from the start.** Serves many people; several moving parts before one hosted job has been measured.
2. **One job at a time in the API's container for the closed beta**, then the queue with one container per job once real jobs have given the worker's size and cost. Chosen; the queue gets its own record.

## Decision

Cloudflare, invite-only, in stages. Each code change is its own pull request, and every hosted feature is a setting that is off locally, so local development keeps working with no new variable set.

1. **This record.**
2. **Closed beta.** The site as Workers static assets; the API and the solvers in one container from one image, one job at a time; run records in Neon; everything behind Access with an invite list. The changes: the image, with a `/healthz` endpoint that needs no database; the Access check and an allowed-origins setting, with the signed-in email on run records and jobs (an amendment to ADR-0026, migration 0005); the API served under `/api` on the site's origin; outputs to R2 and a `jobs` table whose status survives a restart (migration 0006, an amendment to ADR-0050); the Worker, its configuration and a deploy workflow that builds, migrates and deploys from `main`, with secrets set on the platform and never committed; the assistant's key as a platform secret, only if the founder turns the assistant on. Gate: invited engineers take a coupon from chat to package in the browser, and the job's time, memory and fields size are measured on the hosted container.
3. **Scale.** A queue, one container per job, per-user limits and a per-job timeout. Gate: ten jobs submitted at once all finish, and cost per job is measured. Its own record then.
4. **Still invite-only.** More people on the same allow list, a terms and data page (public or non-controlled data only, ADR-0027), error alerts, and the assistant with a spending cap. Gate: a security pass over the API.
5. **Later.** Cloud Run Jobs for jobs above 4 vCPU or 12 GiB; the material monitor as a scheduled job; the same image packaged for ADR-0027's self-hosted customers.

What this record changes in earlier ones: ADR-0006's trigger (finite element analysis) has fired, and the queue it foresaw comes after the beta; ADR-0011's API gains sign-in from Access in front of it, and its loopback-only CORS list becomes a setting; ADR-0025's "hosting is decided at deployment" is decided, Neon; ADR-0027's hosted tier is built now, before the self-hosted packaging, from the same image; ADR-0050's status in memory and files on disk move to a jobs table and R2 for the hosted tier, with one job at a time kept for the beta.

## As built (2026-10-30)

The solver image, the first change of stage 2; no hosted setting yet.

- `Dockerfile` and `.dockerignore` at the repository root; `docker/warm-tectonic.py`, `docker/check-image.py` and `docker/README.md`; `GET /healthz` in `api/src/anisotropy_api/main.py`, answering without the database; `records.git_commit` reads `ANISOTROPY_GIT_COMMIT` where there is no checkout (the image's build argument; a value that is not a 40-digit commit is refused, ADR-0003); the CI job `image` in `.github/workflows/tests.yml`, which builds the image and, with the network off, prints the three solvers' versions and takes the public IM7/8552 coupon through the API to its package with the PDF.
- The base is `ubuntu:24.04`: apt gives the CalculiX 2.21 that CI's runner uses, and the conventions are detected per version (ADR-0030). `python:3.12-slim` was not used, because Debian's package is another CalculiX version. Python 3.12 is uv's managed interpreter, one for the three environments; uv 0.13.0 as on the founder's machine; Tectonic 0.17.0 as in CI. The Gmsh wheel links nine libraries a bare image lacks (GL, GLU, X11 pieces, fontconfig, OpenMP), listed by `ldd`.
- Tectonic's cache is filled by building the public coupon's document once at image build, the run removed again, not by a hand-written warm-up document: the first try missed `cmmib10`, the bold math font `\boldsymbol` loads, and the no-network check found it.
- Measured on the founder's machine (Docker Desktop 29.8.0, WSL 2), 2026-10-30: the image is 2,067,426,434 bytes (2.07 GB: the fea environment 434 MB, api 173 MB, engine 82 MB, Python 123 MB, Tectonic's cache 46 MB). The public coupon job inside the container with the network off ended `done` in 26.3 s (our engine, CalculiX, the record and the package with the PDF); the document is 961,508 bytes, the fields JSON 538,999 bytes, the package zip 978,168 bytes; the container's peak memory was 466,305,024 bytes (445 MiB, cgroup v2, the API included). The same job at image build, with Tectonic downloading, took 80 s. `ccx -v` prints "This is Version 2.21"; `import gmsh` gives 4.15.2; `tectonic --version` gives 0.17.0.
- Observed: with CalculiX 2.21, 54 of the 57 recorded values of the public coupon agree with CalculiX and the reaction differs by +0.23 %; the studio's fixture of 2026-10-28 from the founder's machine with CalculiX 2.22 says 57 of 57 and +0.31 %. Which three values differ, and why: no evidence yet. CI's fea job runs the same 2.21.
- The CI job `image` on GitHub's runner, 2026-10-30 (run 41038205487 of pull request #106, the `api` job green beside it with its fresh database): the warm-up at build 70 s; the image 1,483,502,152 bytes as that Docker reports it (a different storage driver counts differently from Docker Desktop's 2.07 GB); with the network off, `ccx` 2.21, Gmsh 4.15.2, Tectonic 0.17.0, and the public coupon job `done` in 13.0 s with the same 54 of 57 and +0.23 %, the document 961,441 bytes, the fields JSON 538,999 bytes, the package zip 978,140 bytes, peak memory 410,636,288 bytes (392 MiB).

The API behind Access, the second change of stage 2 (the same day):

- `api/src/anisotropy_api/access.py`: a middleware inside the CORS layer that, when `ANISOTROPY_ACCESS_TEAM_DOMAIN` and `ANISOTROPY_ACCESS_AUD` are set (both or neither, ADR-0003), refuses with 401 every request but `GET /healthz` and a CORS preflight that lacks a valid `Cf-Access-Jwt-Assertion` token, and puts the token's email on the request; `ANISOTROPY_ALLOWED_ORIGINS` replaces the loopback CORS list. The email goes to the run records and the jobs (ADR-0026 amendment 1, migration 0005, the actor `browser`).
- The token is checked with PyJWT and its `cryptography` extra: RS256 only, the audience, the issuer `https://<team>.cloudflareaccess.com`, the expiry; the key by the token's key id from `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`, cached, fetched again when an id is unknown, as Access rotates keys every six weeks with seven days' overlap. PyJWT is what Cloudflare's own Python example on its token-validation page uses; `python-jose` and `authlib` were not taken, each a larger surface than one verifier needs, and a hand-written RSA check would be ours to get wrong. The keys are fetched lazily, so starting needs no network; a fetch that fails is a 503 naming the keys' address.
- Not built: a live check behind Cloudflare Access (stage 2's deploy), the `cloudflared` way of validating (the container is not behind a tunnel), and any use of the actor `browser` by the site, which keeps sending `studio` and `calculator`.
- Evidence: `cd api && uv run pytest -q tests` with the test database, 2026-10-30: 256 passed (`tests/test_access.py`, `tests/test_settings.py`, `tests/test_coupon_jobs_api.py`, `tests/test_run_records_db.py`). The Cloudflare pages read on 2026-10-30: [validating the token](https://developers.cloudflare.com/cloudflare-one/identity/authorization-cookie/validating-json/) (the header, the keys' address, RS256, `iss`, `aud`, rotation every six weeks with seven days' overlap) and [the application token](https://developers.cloudflare.com/cloudflare-one/identity/authorization-cookie/application-token/) (the claims; a service token's `common_name` and empty `sub`, no email).

## Consequences

Easier: a browser with WebGL is all a user needs; one image is the hosted product, the self-hosted delivery and a job on a bigger machine; a merge to `main` deploys; a job's files outlive the container; the static site costs nothing per request.

Harder: the API faces the internet for the first time, behind Access, and needs the Access check, per-user limits, a per-job timeout and a security pass (risk R-22); a container's disk is ephemeral, so the outputs and the status need R2 and a jobs table before the beta; files served through the container count as its egress until R2 links replace them; a container that sleeps while a job runs would lose the job, so the beta measures whether the browser's polling keeps it awake (UNVERIFIED); every hosted setting is off unless named, so local development changes nothing; the founder holds the Cloudflare, Neon and GitHub secrets.

Depends on: Cloudflare Workers Paid, Containers, R2 and Access; Neon or another managed PostgreSQL; GitHub Actions for the deploy; the apt CalculiX and the Tectonic release the image pins (risk R-17).

## How we will know it was wrong

If a coupon job needs more than 4 vCPU, 12 GiB or 20 GB, or a cold start or a sleeping container loses jobs the beta cannot tolerate: route jobs to Cloud Run Jobs, same image. If the cost per job measured in stage 2 is more than twice the estimate, or egress from the container is a visible line on the bill: revisit. If Cloudflare labels Containers beta with terms that bar production use before stage 4: Cloud Run. If a GovCloud customer, heavy compute or credits appear: AWS, as the founder said. If Access cannot hold the invite list or its sign-in turns engineers away: an identity provider behind Access. If the two tiers need different code rather than different settings: ADR-0027's test has failed.
