# Component card: local laminate API | version 0.4 | updated 2026-11-05

## Purpose and intended use

Expose the existing engine's stiffness and deformation calculations to local HTTP clients. This is the first integration chunk; see the [step-by-step walkthrough](../../api/README.md).

## Inputs / outputs

`POST /v1/laminates/response`: explicit `SI_BASE` units, one elastic material and source-reference text, bottom-first ply stack and all six load resultants. Returns A/B/D, mid-plane engineering strains, curvatures, accepted inputs and engine package version. Unknown fields and invalid/non-finite values fail with 422. Since ADR-0059 it also returns `summary` (the stack described before any load: ply count, total thickness, symmetric, antisymmetric, balanced, the kind judged on A, the couplings at a stated relative tolerance, and the areal mass from the cited density or the reason it is null) and `first_ply_failure` (under the request's loads, every load scaling together: the criteria the inputs support with R, the ply, its face, z, the mode and the loads at failure; the others listed as not computed with the engine's reason; `evaluated` false with the reason when every load is zero or a ply has no strengths). `material_provenance` carries `density_kg_per_m3` and `fiber_volume_fraction` when the record states them.

`POST /v1/laminates/solve` (ADR-0060): the chat's laminate problem, every value as `{value, unit}` in any unit of the engine's table (`units.py`), a library material or the engineer's own constants (all five strengths or none), the layup bottom ply first, the ply thickness, the six load resultants, an optional f12* and `report_units` (SI, mm-MPa, US or psi). The API converts each value into a case in that system and runs the case solver; it returns the case, every result of `engine_results` in that system with its unit labels, the criteria evaluated, the stack summary and material provenance, the facts and the explanation with its writer (ADR-0052). A unit of the wrong dimension is refused by field name with 422.

`POST /v1/laminates/prescribed-curvature`: explicit `SI_BASE`, `bottom_to_top`, material/source, plies, three forces and three prescribed curvatures. Returns A/B/D, required applied moments, strain and the engine's forward verification with residuals/tolerances. Supplied moments are rejected. Numerical failure returns 422. [Chunk 3 walkthrough](../walkthroughs/chunk-3-constrained-analysis.md).

`POST /v1/cases/solve`: a whole problem in the engine's case format, as `{"case": {...}}` or `{"toml": "..."}`; returns every result the case determines in the case's units, the first-ply criteria evaluated, library provenance per material and the answer-key comparison when the case has `[expected]`. Engine validation messages return as 422. Covers mixed conditions, temperature change, several materials, all four failure criteria and plate buckling (ADR-0024; [note](../api-case-endpoint-2026-10-11.md)).

`POST /v1/wings/analyze` (ADR-0118): a wing, as `{"wing": {...}}` (the wing file's description) or `{"toml": "..."}` (its text), exactly one. The engine reads it by its own rules (`wing_from_dict`), works every flight case by the hand calculation of ADR-0115 and returns the description, the report in the file's units (`wing_report`) and the drawing data (`wing_views`: the airfoil, the walls of the box, the spars, the ribs, the shear center, the centroid, and each case's margins along the span and loads at the root, rounded to four significant digits for drawing). A description the engine refuses is answered 422 in its words. Recorded with the description and a summary, never the drawings.

`POST /v1/wings/shape` (ADR-0118): the same request. The engine reads the description first and refuses it in the same words; then `anisotropy_fea.wing_shape` (ADR-0116) runs in a process of its own (`uv run --project fea --extra mesh`) and the answer is the STEP file's text, in millimetres with every part named, and the part table in the file's units (`parts`: each part's layup, thickness, area and mass, and the whole mass). A refusal of the shape is 422 with its reason; a builder that is missing or stops is 503, one that runs past 90 s 504. Recorded with the description and a summary, never the file.

`POST /v1/wings/checks` (ADR-0119): the same request starts the wing's finite element check, a job of the coupon jobs' kind (ADR-0050, ADR-0056): the engine reads the description first and refuses it with 422 in its words; the answer is 202 with the check as it stands and its `Location`, queued for a solver on the hosted tier. `GET /v1/wings/checks/{id}` answers `state` (queued, running, done, refused, stopped), `stage` among `stages` (build, solve, modes) and, once done, `report`: `anisotropy_fea.wing_check`'s report in the file's units. A refusal's `message` is the reason; a stop's is what to do, its cause in the log. One at a time here (409) and within the per-user limits (429); recorded at `/v1/wings/checks` with the description among the inputs.

`POST /v1/repairs/analyze` (ADR-0135): a stepped patch repair, as `{"repair": {...}}` (the repair file's description) or `{"toml": "..."}` (its text), exactly one. The engine reads it by its own rules (`repair_from_dict`), works the stepped lap by hand (ADR-0130) and returns the description, the report in the file's units (`repair_report`), the drawing data (`repair_views`: the lap's boundaries from the repair's middle and, with a load, the hand calculation's shear stress and patch force along the lap) what a solve of the slice still needs (`solve_needs`, each by the description's path and in words; empty when it can be solved) and what following the bond until it lets go still needs (`bond_needs`, the same way; ADR-0140). A description the engine refuses is answered 422 in its words. Recorded with the description and a summary, never the rectangles or the curve.

`POST /v1/repairs/solve` (ADR-0135): the same request with `cut_faces` (`"open"`, the default, or `"bonded"`). The engine reads the description first; a repair that lacks what the solve needs is answered 422 with the list. Then `anisotropy_fea.repair_model` (ADR-0132) runs in a process of its own (`uv run --project fea`) and the answer is its report in the file's units with its `headline` apart. The tool's own refusal is 422 with its reason; a tool that is missing or stops is 503 with its cause in the log only, one that runs past 120 s 504. Recorded with the description and a summary.

`POST /v1/repairs/bond` (ADR-0140 amendment 1): the repair's request. The engine reads the description first; a repair that lacks what following the bond needs (what a solve needs, less the load, and the adhesive's two strengths and two fracture energies) is answered 422 with the list. Then `anisotropy_fea.repair_bond` runs in a process of its own and the answer is its report in the file's units with its `headline` apart: the load at which the bond first softens and where, the load at which it lets go in this model, the bond's state at both, and the path's curve. The tool's own refusal is 422 with its reason; a tool that is missing or stops is 503, one that runs past 120 s 504. Recorded with the description and a summary, never the curve.
`POST /v1/repairs/plies` (ADR-0141 amendment 1): the repair's request with `finer` (0, 1 or 2: how many steps finer than the run's own mesh). It starts the repair carried until its plies and its bond cannot hold the load, a job of the coupon jobs' kind as the wing's check is (ADR-0119): the engine reads the description first, and a repair that lacks what the run needs (what following the bond needs, and for each ply material its five strengths and four fracture energies) is answered 422 with the list; the answer is 202 with the run as it stands and its `Location`, queued for a solver on the hosted tier. The job runs `anisotropy_fea.repair_plies` with 540 s and 40,000 elements at most (`REPAIR_PLIES_OPTIONS` in `coupon_jobs.py`). `GET /v1/repairs/plies/{id}` answers `state` (queued, running, done, refused, stopped), `stage` among `stages` (build, soften, raise, close) and, once done, `headline` and `report`: the tool's report in the file's units, with the load held, the load not held (null when the run's time came first), how the search `ended`, what had failed at the largest load held (`at_held`) and every load held on the way. A refusal's `message` is the reason; a stop's is what to do. One at a time here (409) and within the per-user limits (429); recorded at `/v1/repairs/plies` with the description among the inputs.

`POST /v1/repairs/shape` (ADR-0135): the repair's solids. `anisotropy_fea.repair_shape` (ADR-0131) runs in a process (`--extra mesh`) and the answer is the STEP file's text, in millimetres with every ply and the adhesive named, and the table of its solids (`parts`). Refusals and failures as the solve's. Recorded with the description and a summary, never the file.

`POST /v1/repairs/changes` (ADR-0136): the repair's request with `change`, one change in the engine's form (`RepairChange`: a quantity set to a value with its unit, steps added, removed or set, or the same plies regrouped). The engine writes the changed repair on a copy and works both by hand (`preview_change`); the answer is the changed description, the change in one sentence, and both summaries (steps, width, load, the largest shear and its place, the load at the adhesive's elastic limit). A change the repair cannot take is answered 422 in the engine's words. Nothing is kept or changed.

`POST /v1/repairs/sweeps` (ADR-0136): the repair's request with `sweep` (`RepairSweep`: one quantity, optionally its range and a load, each with its unit), `confirm` (true unless said) and `cut_faces`. The engine works the repair by hand at every value (`sweep_repair`) and returns a row for each, the sweep in sentences (`words`), the one or two of them that answer it (`answer`) and `cautions`. With a load named, the pick is the smallest repair whose adhesive is still elastic at it, and with `confirm` its slice is solved as `/v1/repairs/solve` does: `check` says what the slice gives and whether it holds the pick (`pick_check`; null `holds` with `close` when the slice's first limit is within 2 % of the load). A solve that cannot run leaves the sweep whole and says the pick is not checked. Recorded with the sweep, its sentences, the pick's row and the check, not every row.

All three analysis endpoints require the `X-Anisotropy-Actor` header (which client sent the request) and record every request that reaches the engine, solved or rejected; the record's id comes back as `run_id` and in the `X-Anisotropy-Run-Id` header. `GET /v1/runs/{run_id}` returns the record as stored: the request as received, which endpoint answered, engine and API versions, git commit, the response or the error. `GET /v1/runs` lists summaries newest first, filtered by `actor`, `endpoint`, `status`, `since`, `until` (offset required) and `limit` (ADR-0026). Behind Cloudflare Access a run record, a coupon job, its package, its files and its explanation are their owner's alone, by the signed-in email: the two lists hold the requester's own and anyone else is answered 404 in the words of an id there is none of; a service token sees what was made with no email; with no sign-in nothing is narrowed (ADR-0104). Each signed-in person's coupons are a folder of their own (ADR-0106): `.local/fea-owners/<key>/<coupon>/` on the disk and `owners/<key>/coupons/<coupon>/...` in the store, `<key>` the first 32 hex digits of the SHA-256 of their email (`storage.owner_key`). `GET /v1/coupons`, a coupon's values, a job, the setup check and the live preview read and write the asker's folder (`CouponJobs.root_of`); the API starts each tool with it in `ANISOTROPY_COUPONS_ROOT` and names it in each request to a warm worker. A request with no email keeps the shared `.local/fea/` and `coupons/`, where a coupon is offered to whoever's jobs alone have run it (ADR-0104).

`GET /v1/materials` and `GET /v1/materials/{material_id}?dataset=`: the library datasets and the SI values the engine would use, each with its page. Both analysis endpoints also accept `material: {"library_id": "...", "dataset_id": null}` in place of explicit constants and then return `material_provenance` (ADR-0020).

`POST /v1/coupon-jobs`, `GET /v1/coupon-jobs/{job_id}`, `GET /v1/coupon-jobs/{job_id}/package`: a coupon job runs `fea/tools/run_coupon.py` in the background on a filled-in input form (base64), the form's rows as one JSON object (`values`, what the studio sends) or a coupon's name, one at a time (409 while one runs; with the hosted tier's job queue, `ANISOTROPY_JOB_ROLE=queue`, the job is answered `queued` and many run at once in solver containers, one per coupon, ADR-0056 amendment 3), and gives its state, its stage and the files made so far, the end of its console, its files and the package as a zip. An ended job has one run record with endpoint `/v1/coupon-jobs` (ADR-0050). Needs uv, the fea environment and CalculiX on the machine.

The list of past analyses (ADR-0109, migration 0012): `GET /v1/coupon-jobs` is what the page's "Your analyses" reads, the requester's own jobs by ADR-0104's rule. A done job's status carries `answer`, the run's answer in seven values as its tool wrote it into the outcome (`basis`, `criterion`, `fails`, `factor`, `ply`, `angle`, `face`), kept on the job's row (`jobs.answer`) by `coupon_jobs.answer_of_outcome` only in that shape and with a finite factor; null for a job that did not end done, one from before the migration, or a result without a criterion. The rows a run ran on are its file `values` (`GET /v1/coupon-jobs/{job_id}/files/values`), served as any file of the job is.

The laminate calculator (`POST /v1/laminates/solve`, ADR-0060) takes a temperature change, `delta_T` with its unit, and a typed material's `alpha1` and `alpha2`, both or neither (ADR-0087); with no load, the answer gives the change at first-ply failure.

The live solve (ADR-0086): `POST /v1/coupon-jobs/live` takes the check's request and answers with the checklist, the preview drawing and, when nothing blocks, our kernel's fields and explanation as `fea/tools/studio_tool.py live` writes them, with the stage seconds; warm `studio_tool.py serve` workers answer it (`ANISOTROPY_LIVE_WORKERS`, default 1, 0 for a fresh process per call), 429 when all stay busy, 504 when one does not answer in 30 s, 503 when none can run; the record keeps the summary and the fields' SHA-256.

The model as a file (ADR-0129): `POST /v1/coupon-jobs/model?program=abaqus|ansys` takes the check's request and answers with the text `fea/tools/studio_tool.py model` writes from those rows, as an attachment named in `Content-Disposition` and in the header `X-Anisotropy-Model-File` (`<designation>-abaqus.inp` or `<designation>-ansys.cdb`); the warm workers of the live solve answer it. A blocked setup or a model the writer refuses is 422 with the sentence to show; the Ansys file is everyone's since ADR-0129 amendment 3, and `GET /v1/coupon-tests` says so in `ansys_model` (403 if it is closed again). The request is recorded with the file's name, size and digest, never its text.

The model's shape for a CAD program (ADR-0146): the same route with `program=step` answers with a STEP file (`model/step`, named `<designation>.step`) that `fea/tools/studio_tool.py model --program step` draws from those rows: each part one solid at its thickness, in millimetres. A STEP file holds no plies, so the part table (each part's layup, ply count, ply and part thickness, material and volume, and whether the finite element model carries it) comes as JSON in the header `X-Anisotropy-Model-Parts`, which the CORS layer exposes beside the name. The header is left out when the table is over 4096 bytes (`MODEL_PARTS_LIMIT`), and the page then points to the file's first lines, which state the same. The rules are the other two files': the tests this request is offered, 422 with the first reason for a blocked setup, 422 with the reason for a shape that cannot be drawn from what the model states, and 503 `The shape builder is not installed here` where Gmsh is not installed with the fea package. The shape is drawn from the checked rows without a mesh, so the element size does not change what it costs. For every program of this route a setup whose mesh would pass 100,000 elements is a 422, judged from the rows before anything is built, with what to change (an element size, or the nodes or the rings round a hole; ADR-0086 amendment 2), and so is a number too large to be one, a tab's material over 80 bytes and a word over 200 bytes in a text row that is written into a file, each with its row's reason. For every file of this route, a 503 because the tool stopped says `The model file could not be written here` and nothing of the cause, which may name a folder of the machine and is logged instead.

A model brought in as a file (ADR-0105): `POST /v1/imported-models?units=<mm-MPa, m-Pa, in-psi or in-ksi>` takes an Abaqus input file as the request's body and its name, percent-encoded, in the header `X-Anisotropy-Model-Name`; the same workers run `studio_tool.py import` on it (`LiveSolver.read_model`), and the answer is `refused` with the reader's reason and line and, in `problem.unread`, every kind of thing the file holds that is not read (ADR-0105 amendment 1), `read` or `solved`, with the reading, the preview and, when solved, the fields and the explanation passed on as written. The file is written to a folder of its own for the answer and removed; the run record keeps its name, size and SHA-256, the reading and the summary, and a refused file is recorded as a rejection. Offered where every test is and to a founder's sign-in (`main._imports`, ADR-0089 amendment 6), 403 otherwise; 413 past 20 MB; 422 for no body, other units or a solve past the workers' time limit; 429 and 503 as the live solve.

For the coupon studio (ADR-0051, ADR-0050 amendment 1): `POST /v1/coupon-jobs/check` runs `fea/tools/studio_tool.py check` on the values and answers with the setup checklist and the preview without a run (for a plate that states no support or no load yet, the preview is its shape alone, passed on as the tool wrote it: ADR-0101 amendment 1) (504 when the tool does not answer within two minutes; recorded by the values' digest); `GET /v1/coupon-jobs` lists the jobs, the requester's own behind the sign-in (ADR-0104); `GET /v1/coupon-jobs/{job_id}/files/{key}` serves one file of a job by key, from the repository or the job's folder only (`fields`, `explanation`, `checklist` and `preview` while it runs, every key once done, `package` as the zip); `GET /v1/coupons` and `GET /v1/coupons/{name}/values` list the coupons on the machine and read one back as the values object. The studio is the actor `studio` (migration 0004).

The fibre tow test (ADR-0074): `POST /v1/tow-tests` runs `fea/tools/studio_tool.py tow` on a tow record (the tow's rows and its specimens as one values object, `test` = "fibre tow tension", an optional `project_id`) and answers at once with its checklist and, when nothing blocks, its result: each specimen's strength and chord modulus, their statistics, the planning loads and, under ASTM D4018-23, each clause judged. No model and no solver; 504 when the tool does not answer within two minutes; recorded by the values' digest.

The workspace's projects (ADR-0062 part 6, migration 0007; a wing since ADR-0122, migration 0014): `GET /v1/projects` lists the requester's projects, the last changed first, by signed-in email behind Cloudflare Access or by actor locally; `PUT /v1/projects/{id}` creates (201) or replaces (200) a project as the page states it (`kind` `fea`, `laminate` or `wing`, `name`, `content` as one JSON object, a wing's description under `content.wing`, `form_version`, `units`), answering 404 for another's project and 409 for a change of kind; `GET /v1/projects/{id}` reads one with the jobs started for it; `PATCH /v1/projects/{id}` renames it. `POST /v1/coupon-jobs/check`, `POST /v1/coupon-jobs` and `POST /v1/wings/checks` take an optional `project_id`: the check writes the derived designation and its run back to the project, the job's row names it; a project the API does not hold blocks nothing. With run records off the routes answer 503: there is no table.

`POST /v1/workspace/proposals` (ADR-0088): a chat message, the rows and conditions the chat offers and the filled rows; the model named for the assistant reads the message in a fixed JSON schema, and the source guard keeps each proposal only when the message writes it: the quote, the number, the unit, the choice. A coupon value in another decimal unit of its own system is converted to the row's unit; a laminate value keeps its unit. The model sees no name, note or source (R-11). The answer also lists, under `unread`, the words of the message the model proposed nothing for, each with a reason by name (`not_offered`, `no_value`, `refers_back`); the guard keeps a part only when its words are in the message (amendment 1). On a plate the request may carry `plate` (the plate's own regions, those of the clicked element, the units of a force and a pressure), and the answer then holds `supports` and `loads` kept by `plate_guard`: the region named by the quoted words or clicked, a load's number written in the quote, a tension's direction and sign taken from the edge (ADR-0101). With no model it proposes nothing. Recorded with the model's name. `GET /v1/workspace/assistant` says whether a model reads messages; not a run.

`POST /v1/workspace/result-questions` (ADR-0100): a chat message and what a question about a result may name (the probe table's quantities, the plies with their angles, whether the model has a gauge section, whether an element is clicked); the model named for the assistant reads the message in a fixed JSON schema of names on offer and whole numbers, and the guard keeps the request only inside the offer, with an element the message writes. No result is sent, shown to the model or returned (a body carrying one is refused); the page runs the request on the results it shows. A request of the kind `failure` (amendment 1: which ply fails first, whether the coupon fails) names nothing, and whatever the model wrote beside it is dropped. With no model nothing is read. Recorded with the model's name when one read it.

`POST /v1/workspace/result-answers` (ADR-0102): a question of why about a result, and the fact sheet of the result the page shows (a job's `explanation.json` facts, or a live solve's; flat values, at most 400 keys and 40 000 characters). The API finds up to three sections of our theory pages by the question's words (`theory.py`: `engine/docs/theory.md`, `fea/docs/theory.md` and `engine/docs/reasons.md`, split at their headings and ranked by BM25) and the model named for the assistant answers in a fixed schema: the answer, the ids of the sections it rests on, and whether they hold the reason. The answer comes back as `prose` only when every number in it is the fact sheet's or the question's (`result_answers.answer_guard`); `sources` are the sections it rests on, or, with no prose (no model, no answer, or `withheld` by the guard), the sections found. The model sees the sheet without a name, a note, a date or a record name. Recorded with the question, the digest of the facts, the sections found and the model's name when one wrote.

`POST /v1/workspace/theory-sections` (ADR-0107): a question, and optionally `limit` (1 to 5, 3 when unset). With `about: "repair"` (ADR-0136) the search is of the repair's own theory sections and of the reference page "Bonded repairs" (`engine/docs/references/bonded-repairs.md`, eleven sections in our own words), which no other search finds (`theory.repair_sections`). The answer is the sections of our theory pages the question's words find, best first, each with its id, document, title and text as a reader is handed it (`theory.find`, the finder of `result-answers`); none when no word of the question is in any section. No result is sent, no model is called and nothing is computed. Recorded with its actor as the question and the ids of the sections found, never their text. The MCP server's `explain_result` calls it ([MCP server card](mcp.md)).

`POST /v1/coupon-jobs/{job_id}/explain` (ADR-0052): the explanation of a job's result or setup, by the template (always) or by the model a deployment names in `ANISOTROPY_ASSISTANT_PROVIDER` and `ANISOTROPY_ASSISTANT_MODEL` with a credential; a model's draft stands only when every number in it is the engine's, else the template's words with the reason. Recorded with the facts' digest, and with `llm_provider` and `llm_model_version` when a model wrote.

A model's setup has typed tools (ADR-0143, `setup_tools.py`): `POST /v1/workspace/setup` reads a setup the request carries (its test, units, size, a plate's regions with where each lies and whether it is an end or a side, what is held and loaded) and `POST /v1/workspace/setup-changes` previews typed changes to it (`hold`, `move`, `force`, `pressure`, `free`, `unload`, `row`; at most 24, every one or none, each refused one with its reason); neither keeps anything. `POST /v1/projects/{id}/setup-changes` does the same on one of the requester's projects and, with `apply`, the preview's `digest` as `base`, `by` and `why`, replaces the content and keeps a version in one transaction (409 when the project changed since the preview, 422 when a change is refused). A project's versions (ADR-0113, on the server since ADR-0143) are `GET` and `POST /v1/projects/{id}/versions` (numbered by the server; the same setup as the last adds none) and `PUT /v1/projects/{id}/versions/{n}/run` (the run made from it and its answer), in the table `model_versions` (migration 0016).

The workspace's planner (ADR-0144, `planner.py`; the contract is `tests/fixtures/planner/`): `POST /v1/projects/{id}/plans` with `{"ask"}` (1 to 1000 characters) on one of the requester's `fea` projects reads the sentence by one call to the model (feature `plan_steps`) into steps of typed tools. A plan is kept only when every step names a tool on offer and a region that exists, every number is written in the sentence and every change previews (ADR-0143); otherwise the model gets one more try with the reasons, then the answer is `refused` with them. The server adds `check` before the run and `qa` after it (at most 12 steps, each with its role and one line). The answer is `proposed`, `question` (asked back), `refused`, `unavailable` (no model) or `capped` (no call: 30 planned requests per signed-in person per day, `ANISOTROPY_AGENT_REQUESTS_PER_DAY`; a service token is not counted). `POST .../plans/{plan_id}/approve` with the plan's `base` applies the changes as a version by `assistant` in one transaction (409 when the plan is not `proposed` or the project changed since), checks the setup on the values the page sends, and starts the run as `POST /v1/coupon-jobs` does; a check that does not pass, or a start refused, stops the plan at that step with the reason. The page reports the steps it carries (`run`, `qa`, `answer`) to `POST .../plans/{plan_id}/steps/{n}`; `GET .../plans/{plan_id}` reads a plan as it stands. Plans are kept in `agent_plans` (migration 0017); the request and the approval are run records under the route's template.
The same routes plan on a `wing` project (build step 5, `planner_kinds.py`): its tools are `add_plies` and `remove_plies` (the engine's ply change, ADR-0128), `analyze` (the hand calculation), `check` (the finite element check, a job counted among the day's analyses) and `answer`; the approval makes the changes and replaces the project's wing in one transaction with the stale check, keeps no version (a wing's versions are the browser's, ADR-0122), then works the hand calculation and starts the check, each run's answer under `runs`, and the page reports the check as its job ends. A repair, which is no kept project, is planned at `POST /v1/workspace/repair-plans` with `{"ask", "repair"}` (the description as the page holds it, its digest the plan's `base`): its tools are the repair's changes (ADR-0136), `sweep`, `use_pick` (the sweep's own pick, which takes no value), `solve`, `bond` and `answer`, and `POST .../repair-plans/{plan_id}/approve` with `{"repair", "base"}` (409 when the description is another) carries every step but the answers and answers the description they leave and each run's answer. Every kind's plans are rows of `agent_plans` (its `kind`: coupon, plate, wing or repair; a repair's has no project and is its asker's), and the day's 30 planned requests count every kind together.

## Dependencies and connections

Uvicorn -> FastAPI -> Pydantic contract -> existing `anisotropy_engine` -> NumPy. Separate `api/pyproject.toml` and `api/uv.lock`; no HTTP dependency added to the engine. pytest and HTTPX2 exercise the app in process.

Run records (ADR-0025, ADR-0026): SQLAlchemy 2 and psycopg 3 reach a local PostgreSQL 17 started by `docker-compose.yml`; Alembic migrations under `api/alembic/` own the `runs` table. Configuration is `DATABASE_URL` and the explicit `ANISOTROPY_RUN_RECORDS=off` switch, read from the environment or the nearest `.env` (python-dotenv). The API refuses to start without a reachable, migrated database unless switched off, and withholds a result (503) when its row cannot be written.

The solver image (ADR-0056): the `Dockerfile` at the repository root builds the API with the engine and fea environments, CalculiX, Gmsh and Tectonic (its TeX files fetched at build by `docker/warm-tectonic.py`, which builds the public coupon's document once), listening on port 8080 as the service user `app`; `GET /healthz` answers without the database; `ANISOTROPY_GIT_COMMIT` gives the run records their commit where there is no `.git`. The CI job `image` runs one public coupon job inside it with the network off (`docker/check-image.py`, [docker/README.md](../../docker/README.md)).

Behind Cloudflare Access (ADR-0056, `api/src/anisotropy_api/access.py`): with `ANISOTROPY_ACCESS_TEAM_DOMAIN` and `ANISOTROPY_ACCESS_AUD` set, a middleware inside the CORS layer refuses with 401 every request but `GET /healthz` and a preflight that lacks a valid `Cf-Access-Jwt-Assertion` token (PyJWT, RS256, the team's published keys matched by key id and refetched when one rotates; 503 when the keys cannot be fetched), and puts the token's email on the request; `record_run` writes it as `user_email` (migration 0005, which also admits the actor `browser`), and a coupon job keeps it for its receipt and status. `ANISOTROPY_ALLOWED_ORIGINS` replaces the local CORS origins. Unset, the API is the local one.

Durable outputs (ADR-0050 amendment 2, `api/src/anisotropy_api/storage.py`): with the four `ANISOTROPY_R2_*` settings, a done job's reported files go by key, with its package zip and the coupon's whole folder, to an object store through the S3 API (boto3, path-style addresses, SigV4), the coupons are restored from the store into `.local/fea/` at startup, and the file endpoints redirect to ten-minute links; a job whose files cannot be stored is `stopped` and its result withheld. With run records on, the `jobs` table (migration 0006) keeps every job's status across restarts, and the rows still `running` when the API starts are marked `stopped` with the reason. The run record stays the immutable receipt.

Uploads from Abaqus (ADR-0094 part 6 and step 5, migration 0010, `api/src/anisotropy_api/uploads.py`): `POST /v1/abaqus-uploads` takes a bundle's zip as the body, judges it with `fea/tools/abaqus_upload.py check`, stores it as `uploads/<id>/bundle.zip` (the bucket, or `.local/abaqus/` through `storage.FolderStore`) with a row in `abaqus_uploads` that names its owner by a project's rule, and puts it beside a finished coupon job's package files with `abaqus_upload.py compare`. The owner alone opens, downloads, compares and deletes it; anyone else gets 404; the emails in `ANISOTROPY_FOUNDER_EMAILS` read every upload. `upload_tokens` keeps the SHA-256 of each token the connector sends with (`POST /v1/connector/uploads`, `Authorization: Bearer`); a cancelled token is refused. Behind Access that one POST passes without Access's token only with `ANISOTROPY_CONNECTOR_UPLOADS=on` (`access.CONNECTOR_UPLOADS`). An upload writes no run record. A machine connected by a code (ADR-0094 amendment 1, migration 0011): `POST /v1/pairing-codes`, signed in, answers a one-time code (ten minutes, one swap, its SHA-256 alone in `pairing_codes`); `POST /v1/connector/pair` says whose account a code is for (`look`) or swaps it for an upload token named for the machine; `GET /v1/connector/runs/<id>/build-script` answers, on an upload token, the build script of the owner's own finished run and 404 for any other. Behind Access these two pass as the upload route does, by `access.connector_route`, which names each path and method. For the page's card (step 6): `GET /v1/abaqus-exchange` says whether uploads are kept, whether the connector's route is open and the three limits; `GET /v1/abaqus-connector` hands out the connector as one zip, written by `abaqus_upload.py connector` once per process (`Uploads.connector`); the list takes `job_id` and `mine`; the sent file's route takes the actor as `?actor=` when a link asks for it (`actor_of_a_link`). The comparison as a PDF (step 7): `POST` and `GET /v1/abaqus-uploads/{id}/document` have `Uploads.document` start `docs/models/upload.py` on the stored comparison at the first ask, keep the PDF as `uploads/<id>/compared-<time>.pdf` (`storage.upload_document_key`) and hand it to the owner and the founders; a document of an earlier comparison is deleted, and the upload's delete removes every object under `storage.upload_prefix`.

Which tests a request is offered (ADR-0089, amendments 5 and 6; `main._every_test`, `main._imports`): every test when the machine's `ANISOTROPY_ALL_TESTS` is on; otherwise the unnotched tension coupon only. Bringing a model in as a file is offered where every test is, and also when the email Cloudflare Access verified is in `ANISOTROPY_FOUNDER_EMAILS`. `GET /v1/coupon-tests` answers both for the requester (`all`, `imports`). The fea tools read the machine's switch; where the API offers every test to a request it starts them with `--every-test` (`coupon_jobs.EVERY_TEST`: before `studio_tool.py`'s command for the check, the tow calculation and a coupon's values, among a job's stored options for `run_coupon.py`, here or in a solver container) and tells a warm live worker per request (`"every": true`, `live.py`). Nothing a request says can place the option.

Per-user limits (ADR-0056, stage 5): `ANISOTROPY_JOBS_PER_USER_PER_DAY`, off unless set, gives each person (the signed-in email, else the actor) one running job at a time and a daily cap, read from the `jobs` table (`running_job_of`, `jobs_started_since`); a request past a limit is a 429 with the reason.

The website's `/calculator` now calls this endpoint. CORS allows credential-free JSON POST requests from localhost/127.0.0.1 on ports 3000/3001. See [the calculator card](calculator.md).

## Out of scope and limits

Local development only. No authentication; a language model only behind the assistant's settings, and then only to rephrase (ADR-0052); no language model yet (the library loader and the run records exist since ADR-0020 and ADR-0026). A job's status is lost when the process stops (ADR-0050). One material per laminate. No hole geometry, ply stress/failure endpoint, thermal/moisture effects or design approval. A caller's citation is not verified evidence; units are declared, not inferred. Extreme finite inputs can still be poorly conditioned; a finite result alone is not a numerical accuracy guarantee.
